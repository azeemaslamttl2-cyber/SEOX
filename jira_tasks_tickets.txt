Ticket: APP-001
Type: Epic
Priority: High
Complexity: Large
Title: Consolidate the four parallel API surfaces into one

Description:
Every backend endpoint is currently declared in up to four places. The
canonical implementation lives in functions/api/**.js as a Pages Function
(`onRequest`). It is then re-exported by a Next route handler in
app/api/<name>/route.js, again by a second Next route handler in
src/app/api/<name>/route.js, and again registered by hand as Connect
middleware in vite.config.js so that `vite dev` and `vite preview` can serve
it. vite.config.js is 2,426 lines and consists almost entirely of these
registrations and their adapters.

The practical cost is that adding or renaming an endpoint requires four
coordinated edits, and forgetting one produces an endpoint that works in
production but 404s in dev (or the reverse). The file even documents a
middleware ordering hazard: "/api/jira/issues" is a prefix of
"/api/jira/issues/status", so the longer path must be registered first or the
status route is shadowed.

This epic covers choosing one runtime (Pages Functions is the deployed one per
CLOUDFLARE.md and wrangler.jsonc), replacing the hand-written vite middleware
with a generic file-system router that discovers functions/api/**, and
deleting the duplicated Next wrappers that are not used by the deployed build.

Acceptance Criteria:
1. A single source of truth exists for each endpoint under functions/api/.
2. The dev and preview servers route /api/* by filesystem convention rather
   than by a hand-maintained registration table.
3. Route resolution matches Pages Functions semantics, including nested
   directories and the longest-prefix case documented in vite.config.js.
4. vite.config.js no longer contains per-endpoint imports or registrations.
5. Unused Next route wrappers are removed, or the Next build is documented as
   a supported target and kept generated rather than hand-written.
6. Every existing endpoint answers identically before and after, verified by
   the existing test suites.

Ticket: APP-012
Type: Story
Priority: High
Complexity: Medium
Title: Rate limit and lock out repeated failed sign-in attempts

Description:
POST /api/auth/login accepts unlimited attempts. The project already has a
fixed-window rate limiter (functions/_lib/rate-limit.js, backed by the
api_rate_limits table) used by the GBP, WPScan and Jira routes, but no
authentication route consumes it. Registration is equally unthrottled, which
allows account enumeration through the 409 "User already exists." response and
bulk account creation.

Implement per-identifier and per-IP throttling on login, registration and the
Google callback, and a progressive lockout on repeated failures for one
account.

Acceptance Criteria:
1. Failed login attempts are counted per email and per client IP.
2. Exceeding the configured threshold returns 429 with a Retry-After header
   and does not reveal whether the account exists.
3. A successful login clears the counter for that identifier.
4. Registration is rate limited per IP.
5. Lockout thresholds and windows are configuration, not literals in the
   handler.
6. Rate-limit state survives a process restart (it is stored in MySQL).

Ticket: APP-013
Type: Story
Priority: High
Complexity: Medium
Title: Implement password reset

Description:
POST /api/auth/password-reset currently returns
`{ ok: true, message: "Password reset is not configured for the local MySQL
auth bridge yet." }` - a 200 response that performs no work. A user who
forgets their password has no recovery path, and the login page has no
"forgot password" affordance.

Build a token-based reset: request a reset by email, store a single-use hashed
token with a short expiry, deliver it by email, and accept a new password
against that token.

Acceptance Criteria:
1. Requesting a reset returns the same response whether or not the email
   exists.
2. A reset token is single use, expires in 60 minutes or less, and is stored
   hashed.
3. Completing a reset updates password_hash with bcrypt at the current cost
   and invalidates every outstanding session for that user.
4. The reset request endpoint is rate limited per email and per IP.
5. The login page links to the reset flow, and the reset pages handle the
   invalid, expired and already-used token states.
6. Passwords are validated against the same policy as registration.

Ticket: APP-020

Priority: High
Complexity: Medium
Title: EXISTING ISSUE - Store and compare users.admin_token as a hash

Description:
31 backend files authenticate with a second credential, `users.admin_token`,
by comparing the submitted value against the column in plaintext:

  SELECT id FROM users WHERE admin_token = ? AND is_active = 1
    AND deleted_at IS NULL LIMIT 1

The migration that introduces the column is named
migration/mysql/20260804_add_admin_token_hash.sql but in fact adds a plaintext
VARCHAR(255) column plus an index on it. Nothing anywhere in functions/ or
src/ references an admin_token_hash column.

The token is a long-lived credential that authorises the Jira ticket surface,
the auditor API, every content tool API, every SEO tool API, the GEO APIs, the
keyword APIs, the Screaming Frog import and the W3C admin validation route. A
database read - a backup, a dump, a SQL injection anywhere - yields working
credentials for all of them.

Acceptance Criteria:
1. admin_token values are stored as a salted hash (or a keyed HMAC suitable
   for constant-time lookup by prefix) and never in plaintext.
2. A shared verification helper is the only place the comparison happens, and
   the comparison is constant time.
3. All 31 call sites use that helper.
4. A migration rehashes or invalidates existing values, with a documented
   operator procedure.
5. functions/_lib/admin-auth.js's ADMIN_TOKEN environment escape hatch is
   reviewed and either removed or given the same treatment.
