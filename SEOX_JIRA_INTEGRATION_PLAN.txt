SECTION 1 - EXECUTIVE SUMMARY
================================================================================

1.1 WHAT JIRA INTEGRATION ADDS TO SEOX
--------------------------------------
SEOX today ends at the finding. The Site Auditor crawls a site, classifies
problems into 25 issue categories with error/warning/notice severities, and
renders them at /auditor/issues and /auditor/issues/:slug. The GBP module
produces scored audit issues and AI recommendations. The WordPress Security
module produces CVE-matched findings. Every one of these stops at "here is what
is wrong".

Nothing in SEOX tracks whether a human ever fixed it. There is no owner, no due
date, no status beyond "present in the last crawl", and no record that a
developer looked at it. A finding that was fixed and a finding that nobody has
touched look identical until the next crawl runs.

Jira integration closes that loop. It gives every SEO finding:
  - an owner (Jira assignee)
  - a workflow state (Jira status)
  - a place where the developer already works (their sprint board)
  - an audit trail of who did what and when
  - automatic verification: when Jira says "Done", SEOX re-checks the URL and
    either confirms the fix or reopens the issue

1.2 WHY THIS MATTERS FOR AN SEO PLATFORM SPECIFICALLY
------------------------------------------------------
SEO work is almost never done by the person who finds it. An SEO consultant
runs the audit; a developer changes the template. The handover between those
two people is where SEO programmes die - findings are exported to a
spreadsheet, emailed, and never seen again.

Jira is where the developer already lives. Pushing the finding into their
backlog, with the exact URL, the current value, the expected value and the
acceptance criteria, removes the handover step entirely. And because SEOX can
re-crawl, it is one of the few tools that can *prove* the fix landed rather
than trusting a status transition.

1.3 THE DIVISION OF RESPONSIBILITY
-----------------------------------
SEOX is the SEO analysis and intelligence layer:
  - detects issues (crawler, audits, third-party APIs)
  - classifies severity and SEO impact
  - generates the recommendation and the acceptance criteria
  - verifies the fix by re-checking the live URL
  - owns the canonical truth of "is this SEO problem still present"

Jira is the task execution and project-management layer:
  - owns the work item, its assignee, its sprint, its board column
  - owns developer discussion (comments)
  - owns the workflow state machine
  - owns reporting on team throughput

Neither system should try to be the other. SEOX must never become a task
manager with its own boards; Jira must never become the source of truth for
whether an SEO issue exists.

1.4 END-TO-END WORKFLOW
------------------------
  SEOX crawls the site
       |
       v
  SEOX detects issue            (buildFindingsFromCrawl, src/lib/auditIssues.js)
       |
       v
  SEOX creates SEO finding      (auditIssues[slug] with severity + urls[])
       |
       v
  User opens /auditor/issues/:slug and clicks "Create Jira Issue"
       |
       v
  POST /api/jira/issues         (fingerprint computed, duplicate check runs)
       |
       v
  Jira issue created            (SEOX stores the mapping row)
       |
       v
  Developer picks it up in their sprint
       |
       v
  Jira status changes           (In Progress -> In Review -> Done)
       |
       v
  Jira webhook fires -> POST /api/jira/webhook
       |
       v
  SEOX synchronises the finding status (open -> in_progress -> resolved_pending)
       |
       v
  SEOX enqueues a verification job and re-checks the affected URL
       |
       v
  Finding verified              (issue genuinely gone -> status 'verified')
       or  Finding still present (-> status 'reopened', comment posted to Jira)
       |
       v
  Jira issue closed by the team, or reopened by SEOX's comment

1.5 THE NON-NEGOTIABLE CONSTRAINT
----------------------------------
Jira is an optional add-on. With no Jira connection configured, every screen,
every API and every crawl in SEOX must behave exactly as it does today. This is
stated again in Section 27 and is a hard acceptance criterion for every phase.

2.5 BACKEND ARCHITECTURE - THE MOST IMPORTANT FINDING  [EXISTING]
------------------------------------------------------------------
The API handlers are written in Cloudflare Pages Functions style:

    export async function onRequest({ request, env }) { ... }

taking a Web Request and returning a Web Response. They live under
functions/api/ and the file path maps to the URL path.

BUT production does not run on Cloudflare Pages. Production runs
"vite preview" on port 4173 (package.json "preview" script;
vite.config.js:2323-2326). vite.config.js is 2360 lines and the bulk of it is
a hand-written adapter that mounts every one of those onRequest handlers as
Connect middleware. The canonical shape (vite.config.js:566-606):

    const SETTINGS_ROUTES = {
      "/api/settings/general": generalSettingsOnRequest,
      "/api/settings/public":  publicSettingsOnRequest,
    };

    function registerSettingsMiddleware(server) {
      for (const [mountPath, handler] of Object.entries(SETTINGS_ROUTES)) {
        server.middlewares.use(mountPath, async (req, res) => {
          try {
            const request  = await createWebRequest(req, mountPath);
            const response = await handler({ request, env: loadDevApiEnv() });
            await sendWebResponse(res, response);
          } catch (error) {
            sendJson(res, error?.status || 500, {
              error: "Settings request failed",
              message: error?.message || "Unknown error",
            });
          }
        });
      }
    }

    function settingsApiPlugin() {
      return {
        name: "seox-settings-api",
        configureServer(server)        { registerSettingsMiddleware(server); },
        configurePreviewServer(server) { registerSettingsMiddleware(server); },
      };
    }

The plugin array is at vite.config.js:2318 (a single long line listing ~57
plugins).

*** CRITICAL RULE FOR JIRA ***
A plugin that implements only configureServer works in "npm run dev" and 404s
in production. Every Jira route must register BOTH configureServer AND
configurePreviewServer. This is not a theory - the codebase carries a comment
about it (vite.config.js:568-571) and a regression test that asserts it
(tests/settingsApiPreview.test.js). The Jira work must ship the same test.

Supporting machinery inside vite.config.js:
  loadDevApiEnv()      vite.config.js:125  merges process.env + loadEnv() +
                       .env + .dev.vars, because Vite does NOT copy .env
                       values into process.env.
  createWebRequest()   vite.config.js:2264 Node req -> Web Request
  sendWebResponse()    vite.config.js:2303 Web Response -> Node res
  readRawBody()        vite.config.js:153  METHODS_WITH_BODY includes DELETE
                       (this API sends JSON bodies on DELETE); multipart
                       bodies are kept as a Buffer, not decoded to UTF-8.
  runNodeHandler()     functions/_lib/node-handler-adapter.js, for the older
                       Express-style handlers in functions/_handlers/.

2.6 AUTHENTICATION  [EXISTING] - THREE SEPARATE MECHANISMS
-----------------------------------------------------------
(a) JWT session - the primary mechanism.
    functions/_lib/auth-token.js
      issueAccessToken(user, env)  HS256 via "jose", 8h expiry, sub = user.id,
                                   claims: email, admin, plan.
      requireUser(request, env)    reads "Authorization: Bearer <jwt>",
                                   verifies, then re-reads the user row
                                   (is_active = 1 AND deleted_at IS NULL).
                                   Returns { uid, id, email, admin, plan,
                                   displayName }.
      requireAdmin(request, env)   requireUser + user.admin check -> 403.
    Signing secret: AUTH_JWT_SECRET, minimum 32 characters, enforced at
    module level.
    It deliberately distinguishes 401 (bad/expired token) from 503 (database
    unreachable) - auth-token.js:44-52. Jira endpoints must preserve that.

    Wrappers: functions/_lib/mysql-storage.js exports verifyAccessToken and
    assertAdmin; functions/_lib/request-auth.js exports
    requireAuthenticatedUser for Node-style handlers.

    NOTE: requireAuthenticatedUser returns a fake
    { uid: "local-dev-user" } when NODE_ENV=development and no Authorization
    header is present (request-auth.js:11-14). Jira endpoints should use
    verifyAccessToken / requireUser directly and NOT inherit that bypass.

(b) admin_token - a body field, for machine / server-to-server callers.
    functions/_lib/admin-auth.js
      normalizeAdminToken(value)    required, max 512 chars
      verifyAdminToken(token, env)  matches env.ADMIN_TOKEN, else
                                    SELECT id FROM users
                                    WHERE admin_token = ? AND is_active = 1
                                      AND deleted_at IS NULL
      requireAdminToken(body, env)  the entry point
      apiErrorResponse(...)         the standard error envelope
      adminApiHeaders()             CORS for a Content-Type-only endpoint
    The file header is explicit: these endpoints accept the admin_token body
    field ONLY - no Authorization header, no cookie, no OAuth token. The token
    is never echoed back and never logged. Backing column: users.admin_token,
    indexed (idx_users_admin_token).
    Used by: the content tool APIs, /api/project-details, /api/auditor
    (which accepts either mechanism - functions/api/auditor.js:33-62).

(c) Machine shared secret - for scheduled / external callers.
    functions/api/gbp/jobs.js:45-60
      timingSafeEqual(a, b)             constant-time compare, hand-written
      authoriseScheduler(request, env)  compares header
                                        X-GBP-Scheduler-Token against
                                        env.GBP_SCHEDULER_TOKEN; if the env
                                        var is unset the runner is DISABLED
                                        rather than left open.
    This is the exact pattern the Jira webhook endpoint must copy.

Issue taxonomy: src/data/auditorData.js (1152 lines).
  SEVERITY = { error, warning, notice }   (auditorData.js:94-116)
  issueCategories (auditorData.js:254) - 15 top-level categories:
    Internal pages, Indexability, Links, Redirects, Content, Social tags,

*** CONSEQUENCE FOR JIRA - READ TWICE ***
There is no server-side table of individual SEO findings. A finding is a
(slug, url) pair inside a JSON blob that the browser produced. Therefore:
  - The browser must POST the finding payload when creating a Jira issue; the
    server cannot look the finding up by an id.
  - The server must store enough of the finding in the mapping row to
    re-verify it later WITHOUT the browser (Section 5.4).
  - The fingerprint must be computed from stable inputs the browser can supply
    and the server can independently recompute (Section 4.4).
This is a genuine architectural constraint, not an inconvenience. Do not
design as if a seo_findings table existed.

2.13 THE GBP MODULE IS THE TEMPLATE FOR JIRA  [EXISTING]
---------------------------------------------------------
Jira should be built as a smaller sibling of GBP. The pieces to copy:

  Credential encryption    functions/_lib/gbp-crypto.js (102 lines)
      AES-GCM via WebCrypto, 32-byte key from GBP_TOKEN_ENCRYPTION_KEY
      (base64), 12-byte random IV, payload format
      "v1.<base64 iv>.<base64 ciphertext>", key cached per process, and a
      decrypt failure returns a clear "encrypted with a different key"
      message rather than a stack trace.
      Exports: encryptionKeyConfigured(env), encryptSecret(env, plaintext),
               decryptSecret(env, payload).

  Connection record        gbp_connections
      UNIQUE (user_id, project_id), access_token_encrypted,
      refresh_token_encrypted, token_expiry, scope, status, status_detail,
      authorized_by_email, connected_at, updated_at.

  Outbound HTTP hardening  functions/_lib/google-fetch.js
      Its header documents a real production incident: the application host
      has no global IPv6 address and a ~324ms RTT to oauth2.googleapis.com,
      while Node's default autoSelectFamilyAttemptTimeout is 250ms, so a bare
      fetch() failed intermittently with ETIMEDOUT. The helper adds a connect
      timeout (DEFAULT_TIMEOUT_MS 15000), bounded retries (DEFAULT_RETRIES 2)
      with RETRY_BASE_DELAY_MS 400, an explicit retryable-code set
      (ETIMEDOUT, ECONNRESET, ECONNREFUSED, ENETUNREACH, EHOSTUNREACH,
      EAI_AGAIN, ENOTFOUND, UND_ERR_CONNECT_TIMEOUT), and deliberately does
      NOT retry HTTP errors - a 401/403/429 is an answer, not a fault.
      *** The Jira outbound client must have the same three guards. ***

  Job queue                gbp_jobs + functions/_lib/gbp-jobs.js (343 lines)
      claimJobs(lockToken, limit) / completeJob / retryJob / deadLetterJob /
      releaseStaleJobs(15) / raiseJobAlert.
      RETRY_BACKOFF_SECONDS = [60, 300, 1800]; max_attempts default 3.
      Idempotency key on enqueue, with ER_DUP_ENTRY treated as success -
      "that is the constraint doing its job, not a failure"
      (gbp-jobs.js:245-248).
      Permanent failures (error.code === 'NEEDS_REAUTH') skip retries and go
      straight to the dead letter; quota/429 waits the longest backoff.
      An unknown job_type is dead-lettered immediately rather than burning
      three attempts.
      Dead letters raise a gbp_job_alerts row, surfaced and acknowledgeable
      at /gbp/operations (src/pages/gbp/GbpOperations.jsx).

  Scheduling               seox-main/worker/gbp-scheduler/index.js
      A cron-only Cloudflare Worker that does nothing but
      POST {SEOX_BASE_URL}/api/gbp/jobs with header X-GBP-Scheduler-Token,
      because Pages Functions have no cron trigger. All logic stays in the
      endpoint.  [CONFIRM] whether this worker is actually deployed against
      the vite-preview production, or whether cron is a system timer on the
      host - see Section 25.

  Rate limiting            functions/_lib/rate-limit.js + api_rate_limits
      Fixed window per (user_id, bucket, window_start) with a UNIQUE key;
      insert-then-read ordering so the limit cannot be beaten by racing.
      LIMITS is an explicit map of named buckets with a written rationale,
      e.g. 'gbp:run-audit': { limit: 6, windowSeconds: 3600 },
           'ai:generate':   { limit: 60, windowSeconds: 3600 }.

2.16 BACKGROUND / ASYNC PROCESSING  [EXISTING]
-----------------------------------------------
Only one real background system exists: the GBP job queue described in 2.13.
Everything else is synchronous request/response, or runs in the browser (the
crawler). There is no Redis, no BullMQ, no worker thread pool, no cron inside
the Node process. A new Jira queue must be the same shape: a MySQL table
drained by an authenticated POST endpoint.

4.1 JIRA CONNECTION
--------------------
AUTHENTICATION METHOD - DECISION
  Two options exist for Jira Cloud:

  (A) Basic auth with an API token: "Authorization: Basic base64(email:token)".
      The user creates the token at id.atlassian.com/manage-profile/security/
      api-tokens. No app registration, no OAuth dance, no refresh, no consent
      screen. Works for Jira Cloud and (with a Personal Access Token as a
      Bearer credential) for Jira Data Center / Server.

  (B) OAuth 2.0 3LO: requires registering an Atlassian app, a consent flow, a
      redirect URI, a cloudid lookup against api.atlassian.com, and refresh
      token rotation.

  RECOMMENDATION: (A) API token for the MVP. Reasons, all grounded in this
  codebase:
    - SEOX already has an OAuth flow it struggles with. functions/_lib/
      google-fetch.js documents an entire production incident caused by
      outbound connect timeouts to oauth2.googleapis.com, and the GBP module
      is currently blocked on a Google quota approval. Adding a second OAuth
      provider multiplies that surface for no user-visible benefit.
    - The admin_settings + AES-GCM pattern for storing a static credential
      already exists and is tested. Token refresh scheduling does not.
    - Jira API tokens do not expire on a timer, so there is no refresh job to
      build, monitor and alert on.
  OAuth 2.0 3LO is recorded as [FUTURE] in Section 30. The
  jira_connections table (Section 12) is designed so that adding it later is
  a column addition, not a redesign.
  [CONFIRM] with the user before building.

SCOPE OF A CONNECTION - DECISION
  Per (user_id, project_id), exactly mirroring gbp_connections
  (UNIQUE KEY uq_gbp_connections_user_project). Rationale: an agency running
  SEOX manages several clients, each with their own Jira. A single global
  connection cannot express that. A per-project connection can still be
  reused across projects by re-entering the same credentials, so the
  per-project model is strictly more capable.
  [CONFIRM] Alternative worth discussing: connection per user, mapping per
  project. That is fewer credentials to manage but cannot serve two Jira
  instances. The table design in Section 12 supports both; the plan assumes
  per-(user, project).

CONNECT
  POST /api/jira/connect {action:"connect"} with baseUrl, email, apiToken.
  Server: normalise the base URL, validate it, call Jira
  GET /rest/api/3/myself to prove the credentials, then encrypt the token
  and upsert the row. Never store an unvalidated credential.

TEST CONNECTION
  POST /api/jira/connect {action:"test"}. Re-runs GET /rest/api/3/myself
  using the stored credential and records the outcome in
  jira_connections.status / status_detail / last_checked_at. Rate limited
  (bucket 'jira:test', see 14.4) so it cannot be used to brute-force.

DISCONNECT
  POST /api/jira/connect {action:"disconnect"}. Behaviour defined in 13.9.

CONNECTION STATUS
  GET /api/jira/status?projectId=... returns:
    { connected, baseUrl, accountEmail, accountDisplayName, status,
      statusDetail, connectedAt, lastCheckedAt, lastSyncAt,
      webhook: { configured, lastEventAt, lastEventType },
      mapping: { ...see 4.2... } | null,
      counts: { linked, open, inProgress, resolved, failed } }
  Never includes the token or any part of it.

VALIDATION RULES for baseUrl
  - must parse as a URL; protocol must be https: (http: allowed only when
    the host is localhost or an RFC1918 address, and then only if
    JIRA_ALLOW_INSECURE_BASE_URL is set - see 13.4 on SSRF)
  - strip any trailing slash and any /rest/... suffix a user pastes
  - reject URLs with credentials in them (user:pass@host)
  - max length 1000, matching the app-settings validator
    (functions/api/settings/general.js:25)

4.2 SEOX PROJECT -> JIRA PROJECT MAPPING
-----------------------------------------
One SEOX project maps to exactly one Jira project. Stored in
jira_project_mappings (Section 12.2). Fields:

  seoxProjectId        user_projects.project_id (varchar)
  jiraProjectId        Jira's numeric project id - the stable identifier
  jiraProjectKey       e.g. "WEB" - display and issue-key prefix
  jiraProjectName      cached for display
  defaultIssueTypeId   Jira issue type id (e.g. Task, Bug)
  defaultIssueTypeName cached for display
  defaultPriorityId    optional; Jira priority id
  defaultAssigneeId    optional; Jira accountId
  defaultLabels        JSON array; always includes "seox" (see 4.3)
  components           JSON array of Jira component ids, optional
  severityPriorityMap  JSON; see Section 10.8
  autoCreateEnabled    boolean, default FALSE
  autoSyncEnabled      boolean, default TRUE
  reopenBehaviour      enum: 'reopen' | 'comment' | 'none'; default 'reopen'
  status               'active' | 'invalid' | 'disabled'
  lastValidatedAt      datetime

Why store BOTH id and key: Jira project keys can be renamed; the numeric id
cannot. Every API call uses the id; every UI string uses the key.

Mapping validation: on save, call Jira to confirm the project exists, the
issue type is valid FOR THAT PROJECT (issue type schemes are per project -
a Task id valid in one project may not exist in another), and the assignee
is assignable (GET /rest/api/3/user/assignable/search). Store status
'invalid' with a reason rather than silently failing later.

4.3 CREATE JIRA ISSUE FROM A SEOX FINDING
------------------------------------------
Issue fields SEOX sets:

  project        from the mapping (by id)
  issuetype      from the mapping, overridable per request
  summary        "[SEOX] <Finding title> - <short URL or N URLs>"
                 max 255 chars, truncated on a word boundary.
                 Example: "[SEOX] Meta description tag missing or empty -
                 /blog/seo-guide"
  description    Atlassian Document Format (ADF) - see below
  priority       from severityPriorityMap, overridable
  assignee       from the mapping, overridable
  labels         always ["seox", "seox-<module>", "seox-<severity>"] plus
                 the mapping's defaultLabels. The plain "seox" label is what
                 makes "show me everything SEOX filed" a one-click JQL query.
  components     from the mapping, if set

DESCRIPTION BODY (ADF). Jira Cloud REST v3 requires ADF, not wiki markup;
v2 accepts a plain string. Build ADF - it is the current API and renders
properly. Sections, in order:

  1. What is wrong            the finding title and a one-line explanation
  2. Affected URL(s)          a bulleted list, each a link. CAP AT 50 with
                              "...and N more - see SEOX" (see the cap
                              discussion below)
  3. Current value            e.g. the existing title tag, its length, the
                              HTTP status, the redirect chain
  4. Expected value           e.g. "a unique description of 120-158 chars"
  5. Why it matters (SEO impact)
  6. Recommended fix          AI-generated in phase 5; a static template
                              before that
  7. Acceptance criteria      a checklist the developer can verify
  8. How to verify            what SEOX will re-check, and that SEOX will
                              re-check it automatically
  9. Source                   module name, crawl date, SEOX project name,
                              and a deep link back into SEOX, e.g.
                              https://<app>/auditor/issues/<slug>
 10. Fingerprint              the finding fingerprint, in a code block

  The fingerprint in the body is deliberate: it makes the link recoverable
  by a human even if the SEOX mapping row is lost, and it is greppable in
  Jira search.

URL LIST CAP - important
  An auditor finding can carry up to 250 URLs (ISSUE_URL_LIMIT in
  src/lib/auditIssues.js:1). Jira's description field has practical size
  limits and a 250-item bullet list is unreadable. Cap the rendered list at
  50 and state the true total. The full list stays in SEOX and, optionally,
  is attached as a CSV ([FUTURE] - attachments need a second API call and
  multipart upload; not in MVP).

SCREENSHOTS / ATTACHMENTS
  [FUTURE]. SEOX does not currently capture screenshots of findings (no
  screenshot code exists in the repository). Do not promise this in the MVP.

4.4 DUPLICATE PREVENTION - THE FINGERPRINT
-------------------------------------------
This is the correctness-critical part of the design. Title matching is
explicitly rejected: titles are localised, AI-rewritten, edited by users in
Jira, and truncated - none of which are stable.

FINGERPRINT DEFINITION
  fingerprint = sha256(
      seox_project_id  + "" +
      source_module    + "" +
      finding_type     + "" +
      scope_key
  )  rendered as 64 lowercase hex characters.

  The  (unit separator) delimiter is already the convention in this
  codebase - functions/_lib/mysql.js:9-16 uses it for the pool connection
  key - and it cannot appear in any of the components, so the encoding is
  unambiguous.

  seox_project_id   user_projects.project_id, verbatim
  source_module     a short stable enum: 'auditor', 'speed', 'wpscan',
                    'robots', 'schema', 'w3c', 'gsc', 'gbp', 'eeat',
                    'duplicate', 'backlinks', 'keywords', 'onpage'
                    NOTE: 'onpage' and 'screaming-frog' findings that
                    duplicate an auditor finding must use 'auditor' so they
                    collapse - see 3.21 and 3.22.
  finding_type      the issue slug from issueSlug() / slugifyIssueTitle()
                    (src/lib/auditIssues.js:15-24), or the module's own
                    stable key (wp_security_findings: the CVE or
                    component_slug; gbp: rec_key or check_key)
  scope_key         the normalised affected URL for a per-URL finding, via
                    normalizeEvidenceUrl() (src/lib/auditIssues.js:216-225 -
                    it strips the hash and any trailing slash except root),
                    then lowercased host.
                    For a site-wide finding (robots.txt, a sitemap problem):
                    the literal string "__site__".
                    For a batched finding covering many URLs: the literal
                    "__batch__" plus a sha256 of the sorted, normalised URL
                    list, so re-running the same batch collapses but a
                    different set of URLs does not.

  The fingerprint is computed SERVER-SIDE from the submitted parts and
  stored alongside those parts, so it can be recomputed and audited. The
  client may compute it too (for optimistic UI), but the server's value is
  authoritative.

STORAGE
  jira_issue_links.fingerprint CHAR(64) with
  UNIQUE KEY uq_jira_link_fingerprint (user_id, fingerprint)
  The unique index - not application logic - is what actually guarantees
  no duplicates. Two concurrent clicks race to INSERT; one wins, the other
  gets ER_DUP_ENTRY and is handled as "already linked". This is exactly how
  gbp-jobs.js:245 treats idempotency-key collisions, and it is the only
  approach that is correct under concurrency.

CREATE ALGORITHM (server side, POST /api/jira/issues)
   1. Authenticate; resolve (user_id, project_id).
   2. Load the mapping; 409 if absent or status != 'active'.
   3. Compute the fingerprint from the submitted parts.
   4. SELECT the existing link row by (user_id, fingerprint).
      4a. No row            -> continue to step 5.
      4b. Row, state 'linked' or 'creating'
                            -> return 200 with { alreadyLinked: true, ... }.
                               Do NOT create. The UI shows "Already in Jira"
                               and a link.
      4c. Row, state 'unlinked' (a user detached it)
                            -> allowed to create a new issue; the row is
                               updated in place with the new issue key and
                               previous_issue_keys appended.
      4d. Row, state 'failed'
                            -> retry is allowed; go to step 5 reusing the row.
   5. Pre-flight remote check (defence in depth, because SEOX's row could
      have been lost or the issue created by another tenant of the same Jira
      project): JQL search
        project = <key> AND labels = "seox" AND
        description ~ "<fingerprint>" ORDER BY created DESC
      If a non-Done issue matches, adopt it: write the link row pointing at
      the existing issue and return { alreadyLinked: true, adopted: true }.
      This step is best-effort: if the JQL search fails, log it and proceed
      to create. Never block issue creation on a search failure.
   6. INSERT the link row with state 'creating' and the fingerprint. If this
      throws ER_DUP_ENTRY, another request won the race - re-read and return
      its result as in 4b.
   7. Call Jira POST /rest/api/3/issue.
   8. On success: UPDATE the row to state 'linked' with issue id, key, self
      URL, status, created_at. Write a jira_sync_log row.
   9. On failure: UPDATE the row to state 'failed' with the error, write a
      jira_sync_log row, and (for retryable failures only) enqueue a
      jira_jobs retry. Return the error to the caller.

REOPEN / REUSE
  When a finding recurs after the linked Jira issue reached a Done-category
  status, the fingerprint still matches. Behaviour is governed by
  jira_project_mappings.reopenBehaviour:
    'reopen'  attempt a Jira transition back to an open status. If no valid
              transition exists (Jira workflows often forbid Done -> To Do),
              fall back to 'comment' and record that in the sync log.
    'comment' post a comment "SEOX re-detected this on <date> at <URL>" and
              set the SEOX finding state to 'reopened'.
    'none'    create a NEW Jira issue, and move the old link row's key into
              previous_issue_keys.
  Default 'reopen'. Never silently do nothing.

WHAT IS DELIBERATELY NOT USED FOR DEDUPLICATION
  - the Jira issue summary/title
  - the AI-generated description text
  - the Jira issue key alone (it does not encode the finding)
  - a client-supplied opaque id (the browser's crawl state is wiped by a
    cache clear; the fingerprint survives that)

4.5 UNLINK
-----------
POST /api/jira/issues/:linkId {action:"unlink"} sets the link row state to
'unlinked' and stops synchronisation. It does NOT delete the Jira issue -
SEOX must never delete data in another system. The row is kept so the
history and previous_issue_keys survive.

4.6 BULK CREATE  [PROPOSED - phase 2, not MVP]
-----------------------------------------------
"Create one Jira issue for all N affected URLs of this finding type" is the
most-wanted shape for content issues (3.1 #5). It uses scope_key
"__batch__<hash>" and is a single Jira issue. A true fan-out ("one issue per
URL") is deliberately NOT offered: it is the fastest way to make a Jira board
unusable and to exhaust the Jira rate limit. If it is ever added it must be
capped hard (<= 20 per action) and confirmed with a modal that states the
count.

SECTION 5 - JIRA <-> SEOX STATUS SYNCHRONISATION  [PROPOSED]
================================================================================

5.1 THE TWO STATUS MODELS
--------------------------
Jira status is per-project and fully customisable. There is no fixed list.
What IS fixed is the status CATEGORY, which every Jira status belongs to and
which the API returns on every status object:

    statusCategory.key = "new" | "indeterminate" | "done"
    (displayed as To Do / In Progress / Done)

*** Map on statusCategory.key, never on the status NAME. ***
A team that renames "In Progress" to "Doing", or adds "Blocked", or uses a
localised Jira, breaks any name-based mapping instantly. The category is
stable across all of that. This is the single most important rule in this
section.

SEOX finding states (new, stored in jira_issue_links.seox_state):

  open              linked, no work started (Jira category "new")
  in_progress       work under way          (Jira category "indeterminate")
  resolved_pending  Jira says done, SEOX has not yet re-checked
  verified          Jira done AND SEOX re-checked and the issue is gone
  reopened          Jira done BUT SEOX re-checked and the issue is still there
  wont_fix          Jira resolution indicates it will not be fixed
  unlinked          the user detached the mapping

5.2 THE MAPPING
----------------
  Jira statusCategory   Jira resolution        -> SEOX seox_state
  ------------------------------------------------------------------
  new                   (any)                  -> open
  indeterminate         (any)                  -> in_progress
  done                  none / Done / Fixed    -> resolved_pending
                                                  then verification runs
  done                  Won't Do / Won't Fix /
                        Duplicate / Cannot
                        Reproduce / Declined   -> wont_fix (NO verification)

The resolution list above is Jira's default set. Because resolutions are also
customisable, the rule is:
  - resolution is null  -> treat as a genuine fix, verify
  - resolution name matches /won.?t|declin|duplicat|cannot reproduce|
    not a bug|invalid/i  -> wont_fix
  - anything else        -> treat as a genuine fix, verify
Store the raw resolution name so a mis-classification can be audited and the
regex tuned without a migration.

REVERSE DIRECTION (SEOX -> Jira)
  SEOX writes to Jira in exactly three cases, and never more:
    (a) issue creation
    (b) a comment when verification fails ("still present after the fix")
    (c) a transition when reopenBehaviour = 'reopen' and the finding recurs
  SEOX must NEVER: change the assignee, change the priority after creation,
  move the issue between sprints, or close a Jira issue. Those belong to the
  team. A tool that silently closes tickets loses the team's trust
  permanently, and a tool that reassigns work causes real friction.

5.3 TRANSPORT: WEBHOOK FIRST, POLLING AS A SAFETY NET
------------------------------------------------------
Webhooks are strongly preferred (Section 6) - they are near-instant and cost
no Jira API quota. But they are not reliable enough to be the only mechanism:
  - Jira does not guarantee delivery and does not retry indefinitely
  - the SEOX host may be down or mid-deploy when an event fires
  - the webhook may not be configured at all (Jira webhook creation needs
    Jira administrator rights, which the SEOX user may not have)

So: a reconciliation poll runs as a floor, not as the primary path.

RECONCILIATION POLL DESIGN
  Job type 'jira_reconcile', one per (user, project), scheduled every 30
  minutes when autoSyncEnabled is on and there is at least one link row in
  state open / in_progress / resolved_pending / reopened.

  It does NOT poll issue by issue. It issues ONE JQL search per project:

    GET /rest/api/3/search/jql
        ?jql=project=<key> AND labels="seox" AND updated >= "-40m"
        &fields=status,resolution,assignee,priority,updated,summary
        &maxResults=100

  and pages while there are more results. A 40-minute window against a
  30-minute cadence gives a 10-minute overlap, so a clock skew or a slow run
  cannot drop an update.

  If a link row has not been seen in any poll for 7 days AND its Jira issue
  cannot be fetched individually (404), mark it 'orphaned' (the issue was
  deleted or moved in Jira) and surface it in the sync errors list. Do not
  guess.

  This design means the poll costs ~2 Jira API calls per project per 30
  minutes regardless of how many findings are linked - which is what keeps
  it inside the rate limit at scale. Per-issue polling is explicitly
  rejected.

  When a webhook event is received for a project, record it in
  jira_connections.last_event_at. If webhooks have been healthy for the last
  hour, the reconcile job may widen its cadence to 6 hours. If no webhook
  event has arrived in 24 hours while issues are known to be changing,
  surface "webhook may not be configured" in the settings UI.

5.4 SEO VERIFICATION - THE PART THAT MAKES THIS WORTH BUILDING
----------------------------------------------------------------
When a link row enters 'resolved_pending', SEOX enqueues a 'jira_verify' job
with a deliberate delay (default 10 minutes, configurable) to let a deploy
and any CDN cache settle.

The verification must run SERVER-SIDE, because the browser is not open when
a developer closes a ticket at 2am. This is the constraint identified in
2.9. The design that satisfies it:

  The link row stores everything needed to re-check, captured at creation
  time in the verification_spec JSON column:

    { "kind": "url_check",
      "url": "https://example.com/blog/seo-guide",
      "checks": [
        { "type": "meta_description_present" },
        { "type": "meta_description_length", "min": 70, "max": 158 }
      ] }

  Verification kinds (MVP set - deliberately small):
    http_status        re-fetch the URL; assert the status is 2xx (covers
                       404 page, 4XX page, 5XX page, Timed out, broken
                       CSS/JS/image, broken redirect)
    redirect_chain     follow redirects; assert the chain length and the
                       final status (covers redirect loop, chain too long)
    head_tag_present   parse the HTML head; assert a tag exists and is
                       non-empty (title, meta description, H1, canonical,
                       og:*, twitter:*)
    head_tag_length    as above plus a length bound
    robots_directive   assert noindex/nofollow are absent from both the
                       meta robots tag and the X-Robots-Tag header
    canonical_target   resolve the canonical and assert it is self-
                       referencing or 200
    image_alt          assert the named images now carry alt text
    manual             no automatic check possible; go straight to
                       'verified' on the Jira transition and say so in the UI

  The fetch reuses the EXISTING server-side fetcher rather than adding a new
  one: functions/api/crawler/fetch.js and functions/_lib/url-security.js
  (parsePublicHttpUrl / fetchPublicHttpUrl - already imported by
  vite.config.js:82 and already enforcing the public-URL/SSRF guard). The
  HTML parsing reuses whatever functions/_handlers/fetch-url-meta.js and the
  auditor engine already use. DO NOT write a second HTML parser.

  Outcome:
    all checks pass  -> seox_state = 'verified', verified_at = now,
                        post an optional Jira comment "SEOX verified this fix
                        on <date>" (configurable, default ON - it is the
                        payoff of the whole integration and teams love it)
    any check fails  -> seox_state = 'reopened', post a Jira comment stating
                        exactly which check failed and what was found, and
                        apply reopenBehaviour
    fetch fails      -> retry per the job backoff; after max attempts set
                        'resolved_pending' with a verification_error and
                        surface it in the sync errors list. Do NOT reopen a
                        ticket because SEOX could not reach the site - that
                        would be a false accusation.

  A finding whose verification_spec.kind is 'manual' skips all of this.
  Being honest about what cannot be auto-verified is better than a
  meaningless green tick.

5.5 CONFLICT RESOLUTION
------------------------
  Jira is authoritative for: status, resolution, assignee, priority,
  summary, comments.
  SEOX is authoritative for: whether the SEO problem still exists.

  These cannot actually conflict, because they are different facts. The
  'reopened' state exists precisely to represent the interesting
  disagreement: "Jira says done, the site says otherwise." Do not try to
  collapse it.

  Event ordering: every inbound event carries the Jira issue's `updated`
  timestamp. jira_issue_links.remote_updated_at holds the last one applied.
  An event whose `updated` is older than the stored value is discarded as
  out of order. This makes a webhook and a poll delivering the same change
  harmless, and makes out-of-order webhook delivery harmless too.

SECTION 6 - JIRA WEBHOOKS  [PROPOSED]
================================================================================

6.1 SHOULD WEBHOOKS BE USED?
-----------------------------
Yes - as the primary transport, with the reconciliation poll of 5.3 as the
floor. Rationale: a status change must show up in SEOX within seconds for the
verification loop to feel like a loop rather than a batch job, and polling
every project every minute would be both wasteful and rate-limited.

But the integration must WORK WITHOUT THEM. Webhook registration in Jira
Cloud requires Jira administrator permission (Settings > System > WebHooks).
Many SEOX users will not have it. Therefore:
  - webhooks are OPTIONAL
  - the settings UI shows the webhook URL and secret for an admin to paste in
  - if no webhook events ever arrive, the poll keeps everything correct, just
    slower
  - the UI must say which mode is active, honestly

6.2 EVENTS TO SUBSCRIBE TO
---------------------------
  jira:issue_updated     REQUIRED. Carries status transitions, assignee,
                         priority and resolution changes. The changelog in
                         the payload says exactly which fields moved.
  comment_created        RECOMMENDED. Needed for Section 7.
  jira:issue_deleted     RECOMMENDED. Lets SEOX mark the link 'orphaned'
                         immediately instead of discovering it 7 days later.
  jira:issue_created     NOT NEEDED. SEOX creates its own issues and learns
                         the key from the API response. Subscribing would
                         just add load.
  comment_updated /
  comment_deleted        OPTIONAL. Only if comment mirroring is enabled and
                         the team cares about edits.

  Jira does not have separate "transitioned", "assigned", "reopened" or
  "resolved" webhook events - all of those arrive as jira:issue_updated with
  a changelog. Do not design as if they were distinct events.

  JQL filter: register the webhook with the filter  labels = "seox"  so Jira
  only sends events for issues SEOX cares about. This cuts inbound volume
  dramatically on a busy project and is set in the Jira webhook UI.

6.3 ENDPOINT
-------------
  POST /api/jira/webhook
  Public - it must be reachable by Atlassian's servers, so it cannot require
  a SEOX session.

  File: functions/api/jira/webhook.js
  Registered in vite.config.js for BOTH configureServer and
  configurePreviewServer (Section 2.5).

6.4 AUTHENTICATION AND SECURITY
--------------------------------
Jira Cloud's plain WebHooks do NOT sign their payloads (only Connect/Forge
apps get signed requests). So the endpoint must authenticate by a secret that
travels in the URL, plus defence in depth.

  (a) Secret path token. The registered URL is
        https://<host>/api/jira/webhook?t=<32-byte-random-hex>
      The token is generated per connection, stored in
      jira_connections.webhook_secret (encrypted at rest with the same
      AES-GCM helper), and compared with a CONSTANT-TIME comparison - reuse
      the timingSafeEqual pattern at functions/api/gbp/jobs.js:45-53.
      A mismatch returns 401 with no body and no detail.

  (b) Optional shared-secret header. If a global JIRA_WEBHOOK_SECRET env var
      is configured, also require header X-SEOX-Webhook-Secret to match it,
      again constant-time. Some deployments can inject a header via a proxy;
      where they can, use it.

  (c) Payload sanity. The body must be JSON with a recognised
      webhookEvent and an issue.id. Anything else is 400.

  (d) The webhook NEVER trusts the payload's content for authorisation. It
      resolves the owning user and project from the SEOX side:
      SELECT ... FROM jira_issue_links WHERE jira_issue_id = ?
      combined with the connection the token belongs to. If the issue id is
      not linked to the connection that owns the token, the event is
      ACKNOWLEDGED (200) and ignored. Returning 200 for an unknown issue is
      deliberate: a non-200 makes Jira retry forever for events that will
      never be relevant.

  (e) Rate limiting / flood protection. A per-connection cap (default 600
      events/hour) via the existing rate-limit table with bucket
      'jira:webhook'. Over the cap, the endpoint returns 200 and drops the
      event, and raises one alert row (not one per event). Dropping is safe
      because the reconcile poll will catch up.

  (f) No secrets in logs. The webhook token must never be logged, and the
      request URL must be redacted before any console.error.

6.5 EVENT VALIDATION
---------------------
  1. Method must be POST; anything else 405. OPTIONS returns 204.
  2. Content-Type must be application/json.
  3. Body size cap: reject > 1 MB (Jira payloads with large changelogs and
     rich-text comments can be big, but not that big).
  4. Parse; require webhookEvent and issue.id.
  5. Resolve the connection from the token; 401 if unknown.
  6. Resolve the link row; 200-and-drop if unlinked.

6.6 IDEMPOTENCY
----------------
Jira retries on non-2xx, and a proxy can duplicate a request. Every event
must be exactly-once in effect.

  Event key: sha256(jira_issue_id + "" + webhookEvent + "" +
                    timestamp_from_payload + "" + changelog.id)
  where changelog.id is present on issue_updated and comment.id on comment
  events; for events with neither, use the payload timestamp alone.

  Stored in jira_webhook_events.event_key with
  UNIQUE KEY uq_jira_webhook_event (event_key).
  An INSERT that raises ER_DUP_ENTRY means "already seen" -> return 200
  immediately. Same pattern as gbp-jobs.js:245.

  Belt and braces: the remote_updated_at ordering check of 5.5 means that
  even a duplicate that slips through cannot apply a stale change.

6.7 PROCESSING MODEL - ACKNOWLEDGE FAST, WORK LATER
-----------------------------------------------------
The endpoint must return within a second or two. Jira's webhook timeout is
short and a slow endpoint gets events dropped.

  Synchronous part (inside the request):
    validate -> insert jira_webhook_events row (status 'pending') -> 200 OK

  Asynchronous part (the job runner):
    a 'jira_webhook' job processes pending event rows:
      - apply the status/resolution/assignee/priority change to the link row
        (subject to the remote_updated_at ordering check)
      - on a transition into a Done category, enqueue 'jira_verify'
      - on comment_created, upsert the comment cache (Section 7)
      - mark the event row 'processed' with processed_at
    Failures mark the row 'failed' with an error and are retried by the same
    backoff as every other job.

  This split also makes replay possible: an event row that was stored but
  never processed can be reprocessed by hand from the sync errors screen.

6.8 RETRY AND FAILURE HANDLING
-------------------------------
  Inbound: SEOX returns 200 for everything it has durably stored, and 5xx
  only if it genuinely could not store the event (database down). A 5xx
  makes Jira retry, which is the correct behaviour in that one case.
  Jira Cloud retries a failed webhook a limited number of times over a
  short window and then gives up permanently - which is precisely why the
  reconcile poll of 5.3 is not optional.

  Outbound (SEOX -> Jira, e.g. posting the verification comment): the
  standard job retry - RETRY_BACKOFF_SECONDS [60, 300, 1800], max 3
  attempts, then dead letter with an alert row.

6.9 WEBHOOK HEALTH
-------------------
  jira_connections.last_event_at is written on every accepted event.
  The settings panel shows:
    "Webhook: receiving events (last: 4 minutes ago)"          healthy
    "Webhook: no events received yet - using scheduled sync"   not configured
    "Webhook: no events for 3 days - check the Jira webhook"   suspicious
  Never claim a webhook is configured just because the URL was displayed.

SECTION 7 - JIRA COMMENTS <-> SEOX  [PROPOSED]
================================================================================

7.1 REQUIRED FUNCTIONALITY (MVP)
---------------------------------
SEOX -> Jira, system comments only. SEOX posts a comment in exactly three
situations, all of them automatic and all of them factual:

  (a) Verification passed
      "SEOX re-checked <URL> on <date> and this issue is no longer present."
  (b) Verification failed
      "SEOX re-checked <URL> on <date> and this issue is STILL present.
       Expected: <expected>. Found: <actual>."
  (c) Finding recurred after closure (reopenBehaviour = 'comment', or
      'reopen' where no transition was available)
      "SEOX detected this issue again on <date> at <URL>."

Each is posted through POST /rest/api/3/comment with an ADF body, and each
is recorded in jira_sync_logs. (b) is the one that earns the integration its
keep - it is the moment SEOX tells the team something they did not know.

No user-authored SEOX comments are pushed in the MVP. SEOX has no commenting
UI to push from.

7.2 RECOMMENDED FUNCTIONALITY (phase 3)
----------------------------------------
Jira -> SEOX, read-only comment display.

  Workflow: developer comments in Jira -> comment_created webhook ->
  SEOX caches the comment -> the SEO finding detail panel shows the latest
  Jira activity.

  Implementation: a small cache on the link row rather than a full comment
  table. jira_issue_links.last_comment JSON holding
    { id, authorDisplayName, authorAccountId, createdAt, bodyText }
  plus comment_count.

  Why a cache and not a table: SEOX does not need comment history - Jira has
  it, and there is a link to Jira one click away. Storing every comment
  means storing arbitrary third-party user content indefinitely, which is a
  data-retention and privacy liability for no benefit. If a full thread is
  ever wanted, see 7.4.

  Body handling: Jira returns ADF. Flatten it to plain text for display -
  do NOT render third-party rich text as HTML in the SEOX UI (XSS). Truncate
  to 500 characters with an "open in Jira" link.

  Author display: store the display name and accountId. Do NOT store email
  addresses of Jira users - they are third-party personal data SEOX has no
  need for.

7.3 OPTIONAL FUTURE FUNCTIONALITY
----------------------------------
  [FUTURE] A comment box in the SEOX finding panel that posts to Jira as the
           connected account. Needs a clear UI warning that the comment will
           appear under the service account's name, not the SEOX user's -
           which is confusing enough that it may not be worth building.
  [FUTURE] Full comment thread mirroring in a jira_comments table.
  [FUTURE] @mention translation between the two systems. Almost certainly
           not worth it.

7.4 CLEAR SEPARATION
---------------------
  REQUIRED     SEOX -> Jira system comments (verification result, recurrence)
  RECOMMENDED  Jira -> SEOX latest-comment display, read-only, cached
  OPTIONAL     SEOX -> Jira user-authored comments
  FUTURE       full thread mirroring, mention mapping

7.5 VOLUME CONTROL
-------------------
A comment on every sync would be spam. Rules:
  - at most one verification comment per link row per verification run
  - no comment when nothing changed
  - no comment for a 'manual' verification kind (there is nothing to report)
  - the verification-comment behaviour is a per-project setting
    (postVerificationComments, default true) so a team that finds it noisy
    can turn it off without turning off verification

8.1 REUSE, DO NOT REBUILD
--------------------------
SEOX already has a complete DeepSeek integration (Section 2.14). The Jira
work adds ONE new module that calls the EXISTING helpers:

  functions/_lib/jira-ai.js   [PROPOSED]
    imports resolveDeepSeekApiKey from functions/_lib/deepseek-key.js
    follows the call pattern of functions/_lib/gbp-ai.js:26-75 exactly:
      - AbortController, 60s timeout
      - system instruction suffixed "Return valid JSON only."

Adding a second AI client, a second key resolver or a second rate-limit

8.2 WHAT THE AI GENERATES
--------------------------
Requested as one JSON object, in one call (one call, not eight - latency and
cost both matter, and the fields are correlated):

  {
    "summary":            "<= 200 chars, no [SEOX] prefix - SEOX adds it",
    "technicalDescription": "2-4 sentences for a developer",
    "rootCause":          "the most likely cause given the evidence",
    "recommendedFix":     "concrete implementation steps",
    "developerInstructions": ["step 1", "step 2", ...],
    "acceptanceCriteria": ["criterion 1", "criterion 2", ...],
    "seoImpact":          "1-2 sentences, concrete, no hype",
    "testingInstructions": ["how to verify manually", ...]
  }

8.3 WORKED EXAMPLE
-------------------
  SEOX detects (from src/lib/auditIssues.js:169-171):
    slug     "meta-description-missing"
    title    "Meta description tag missing or empty"
    severity "warning"
    url      https://example.com/blog/technical-seo-guide
    evidence metaDescriptionCount: 0, titleText: "Technical SEO Guide",
             page word count and H1 available from the crawl row

  AI is given: the slug, title, severity, the URL, the page title, the H1,
  a short content extract, the site's domain, and the SEO rule being applied.

  AI returns (illustrative):
    summary  "Add a meta description to the Technical SEO Guide article page"
    technicalDescription
             "The page at /blog/technical-seo-guide renders no
              <meta name=\"description\"> tag. Google therefore composes the
              SERP snippet from arbitrary body text, which typically lowers
              click-through rate for informational queries."
    rootCause
             "The blog article template does not output a description meta
              tag, either because the field is empty in the CMS for this post
              or because the template omits the tag entirely."
    recommendedFix
             "In the article template, output
              <meta name=\"description\" content=\"{{ post.excerpt }}\">
              inside <head>, falling back to the first 155 characters of the
              post body when the excerpt is empty. Then set an excerpt for
              this post."
    acceptanceCriteria
             ["<meta name=\"description\"> is present in the HTML source",
              "content is between 70 and 158 characters",
              "content is unique across the site",
              "content mentions the page's primary topic"]
    seoImpact
             "Missing descriptions do not directly reduce rankings, but
              Google-generated snippets usually convert worse than authored
              ones. Affects click-through on every impression this page gets."
    testingInstructions
             ["View source on the live URL and search for name=\"description\"",
              "Run the URL through SEOX > Site Auditor and confirm the finding
               has cleared"]

  SEOX renders that into the ADF body of Section 4.3, and sets
  verification_spec to
    { kind:"url_check", url:"...",
      checks:[{type:"head_tag_present", tag:"meta[name=description]"},
              {type:"head_tag_length", tag:"meta[name=description]",
               min:70, max:158}] }

8.4 CONTROLS
-------------
  OPT-IN, PER ACTION. The create dialog has an "Enhance with AI" toggle,
  default OFF for the first release. AI costs money and adds 3-10 seconds of
  latency; a user in a hurry should not be forced through it.

  PREVIEW AND EDIT. The generated text is shown in the create dialog and is
  editable before submission. Never post AI output to a third-party system
  without the user seeing it.

  FALLBACK. If AI is unconfigured, rate-limited, slow or returns malformed
  JSON, fall back silently to the static template of Section 4.3. Creation
  must never fail because AI failed. This is a hard rule.

  NO AI IN THE AUTOMATIC PATH - at least not in phase 5. An auto-created
  issue uses the static template. Reasons: auto-creation runs in a
  background job where nobody can review the output; AI latency in a job
  that may create several issues multiplies; and an AI hallucination posted
  unreviewed into a client's Jira is a reputational problem. Revisit only
  after the manual path has been in production long enough to trust the
  prompt.

  TRUNCATION. Cap every AI field server-side before it reaches Jira
  (summary 200, each list 10 items, each string 2000 chars). The model can
  and will ignore length instructions.

  ATTRIBUTION. The Jira description footer states
  "Description drafted by SEOX AI and reviewed by <user>" when AI was used.
  Teams are entitled to know.

8.5 WHAT THE AI IS NOT ALLOWED TO DECIDE
-----------------------------------------
  - the priority (comes from severityPriorityMap - deterministic)
  - the assignee (comes from the mapping)
  - the labels (deterministic; the "seox" label must always be present)
  - the fingerprint (computed, never generated)
  - whether to create the issue at all
  - the verification_spec (derived from the finding type by code, because
    a hallucinated verification rule would produce false "verified" results)

11.21 RATE LIMITING CONSIDERATIONS (Jira's own limits)
--------------------------------------------------------
  Jira Cloud applies per-tenant rate limits and answers with 429 plus a
  Retry-After header. The client MUST honour Retry-After rather than using
  its own backoff for that case - this is the single most common cause of
  an integration being throttled harder. Implementation detail in 14.5.
  SEOX's own buckets (11.0) exist to stop one SEOX user exhausting the
  shared tenant allowance before Jira ever sees it - the same reasoning the
  existing rate-limit.js header gives for the GBP and WPScan buckets.

-----------------------

    uq_jira_link_fingerprint   THE duplicate-prevention guarantee (4.4).
                               Scoped by user_id, not globally, so two
                               tenants auditing the same public URL do not
                               collide.
    uq_jira_link_issue         stops two SEOX findings pointing at one Jira
                               issue within a connection, which would make
                               webhook routing ambiguous. jira_issue_id is
                               NULL while state='creating' and MySQL allows

    idx_jira_link_issue_lookup the webhook's hot path: resolve a link from
                               an inbound issue id.
    scope_key_hash             scope_key can be a 2048-char URL, which is

                               utf8mb4 (3072-byte index limit). The hash
                               column is what gets indexed when a lookup by

                               display and audit.

  COLUMN NOTES
    state         lifecycle of the LINK:
                  'creating' | 'linked' | 'failed' | 'unlinked' | 'orphaned'
    seox_state    the SEO finding state of 5.1:
                  'open' | 'in_progress' | 'resolved_pending' | 'verified' |
                  'reopened' | 'wont_fix' | 'unlinked'
                  Two columns, not one, because they answer different
                  questions: "did we manage to file it" vs "is the SEO
                  problem fixed". Collapsing them loses information.
    finding_snapshot  the finding as it was when filed - title, severity,
                  current value, expected value, evidence, crawl timestamp.
                  Needed to show "what we filed" long after the crawl state
                  has been overwritten, and to diff on recurrence.
    verification_spec  see 5.4. This column is what makes server-side
                  verification possible at all.
    creation_mode 'manual' | 'auto'
    previous_issue_keys  JSON array, appended when reopenBehaviour='none'
                  creates a replacement issue.
  RETENTION  keep indefinitely while the project exists. These rows ARE the
             history of the SEO programme. Deleted with the user by cascade;
             deleted with the project by the application (there is no FK from
             project_id since it is not a primary key).

12.7  SHARED CRYPTO - A REFACTOR, NOT A NEW MODULE
----------------------------------------------------
functions/_lib/gbp-crypto.js is entirely generic apart from reading the
env var name GBP_TOKEN_ENCRYPTION_KEY and mentioning GBP in two error
strings. Two options:

  (A) [RECOMMENDED] Generalise it to functions/_lib/secret-crypto.js with
      encryptSecret(env, plaintext, { keyName })   and matching decrypt,
      then re-export the existing GBP-named functions from gbp-crypto.js so
      no GBP call site changes. Jira passes keyName
      'JIRA_TOKEN_ENCRYPTION_KEY'.
  (B) Copy the file as jira-crypto.js.
  (A) is correct - (B) is duplicate business logic, which the brief
  explicitly forbids. The refactor is ~20 lines and is covered by the
  existing GBP behaviour.
  [CONFIRM] Alternatively reuse GBP_TOKEN_ENCRYPTION_KEY itself for Jira.
  Simpler to operate (one key), but couples the two integrations' key
  rotation. Recommend a separate key.

12.8  NO CHANGES TO EXISTING TABLES
-------------------------------------
Nothing in this plan alters an existing table. In particular:
  - user_projects is untouched. Jira settings live in
    jira_project_mappings, not in project_data, because they must be
    queryable by the background job runner and project_data is an
    unindexed JSON blob.
  - users is untouched.
  - admin_settings is untouched. Jira credentials are per-user/per-project,
    not application-wide, so SETTING_DEFINITIONS gains nothing.
    (One possible exception: a global default Jira base URL for an install
    that only ever talks to one Jira. Rejected in Section 10 as a second
    source of truth.)
  - api_rate_limits is untouched - only new bucket NAMES are added in code.

12.9  TABLES CONSIDERED AND REJECTED
--------------------------------------
  jira_comments        Rejected. Jira owns comment history and is one click
                       away. A cached last_comment on the link row covers
                       the display need (7.2) without storing third-party
                       user content indefinitely.
  jira_sync_failures   Rejected. A failure is a jira_sync_logs row with
                       result='error' plus a jira_jobs row in status 'dead'.
                       A third table would be a denormalised view of two
                       existing ones and would drift.
  jira_audit_logs      Rejected. jira_sync_logs already carries actor_email,
                       actor_kind, action, result, target and timestamp -
                       which is precisely an audit log. Two tables would
                       split the trail.
  jira_job_alerts      Rejected for the MVP. gbp_job_alerts exists because
                       GBP has a dedicated operations screen. Jira dead
                       letters surface through jira_sync_logs filtered to
                       result='error' in the settings error card, which is
                       enough at this scale. Revisit if a Jira operations
                       page is ever built.
  jira_status_map      Rejected. Mapping is on statusCategory (5.1), which
                       is a fixed three-value enum - a JSON column on the
                       mapping row would be enough even if it were needed,
                       and it is not.

12.10 MIGRATION SAFETY
-----------------------
  - All six statements are CREATE TABLE IF NOT EXISTS. The migration is
    idempotent and adds nothing to existing tables, so it cannot break a
    running deployment and needs no downtime.
  - It must be reviewed and run manually. Do NOT add an auto-migrate step;
    the project has no migration runner (migration/add_index.mjs is a
    one-off script, not a framework).
  - Rollback is DROP TABLE on the six tables; no existing data is touched.
  - Before running: confirm 2.2(a), confirm the character set of the target
    database matches (utf8mb4 / utf8mb4_general_ci - verified in
    mysql_tables.sql:19).


================================================================================
SECTION 13 - SECURITY DESIGN  [PROPOSED]
================================================================================

13.1 CREDENTIAL STORAGE
------------------------
  A Jira API token grants full read/write to the user's Jira as that user.
  It is at least as sensitive as the GBP refresh token, and it is treated
  the same way:
    - AES-GCM encrypted at rest (12.7), key from
      JIRA_TOKEN_ENCRYPTION_KEY, 32 bytes base64
    - the key lives only in the server environment, never in the database
    - decryption happens only inside functions/_lib/, never in a handler
      that could return the value
    - a decrypt failure produces the gbp-crypto.js style message ("encrypted
      with a different key - reconnect") rather than a stack trace
  REJECT the gsc_connections precedent of plaintext TEXT token columns.

13.2 NEVER EXPOSE CREDENTIALS TO THE FRONTEND
-----------------------------------------------
  Hard rules, to be enforced by a test (24.6):
    - no Jira endpoint response contains api_token, webhook_secret, or any
      substring of either
    - the webhook URL with its secret is returned exactly twice: on connect
      and on regenerate. Every other read returns it masked.
    - no VITE_JIRA_* environment variable exists. Anything VITE_-prefixed is
      compiled into the browser bundle. The existing .env.example already
      demonstrates the distinction (VITE_GOOGLE_CLIENT_ID is public,
      GOOGLE_CLIENT_SECRET is not).
    - the browser never sends a Jira credential to Jira directly; all Jira
      traffic is server-to-server. Beyond secrecy, this also avoids CORS
      entirely.

13.3 API AUTHORIZATION
-----------------------
  Every /api/jira/* endpoint except the webhook and the job drain:
    1. verifyAccessToken / requireUser -> 401 on failure, 503 if the auth
       database is unreachable (preserve the distinction)
    2. resolve user_id from the token ONLY
    3. verify the caller owns projectId:
         SELECT 1 FROM user_projects
          WHERE user_id = ? AND project_id = ? AND owner_uid = ?
       -> 403 if absent. This check must be in a shared helper
       (functions/_lib/jira-request.js requireJiraProject) so it cannot be
       forgotten on a new route - the same role gbp-request.js plays.
    4. every subsequent query carries user_id in its WHERE clause. No query
       trusts an id from the request body alone. Note that link ids are
       sequential bigints, so an IDOR here would be trivially exploitable;
       WHERE id = ? AND user_id = ? is mandatory, not optional.

13.4 SSRF - A REAL RISK HERE
-----------------------------
  The user supplies baseUrl and the server then makes requests to it. That
  is textbook SSRF. Mitigations:
    - reuse functions/_lib/url-security.js parsePublicHttpUrl, which the
      proxy and crawler endpoints already use for exactly this reason
      (imported at vite.config.js:82)
    - require https: (exception in 9.1 for localhost, gated behind an env
      flag that is off by default)
    - reject private/loopback/link-local/metadata addresses (169.254.169.254
      in particular) - parsePublicHttpUrl should already do this; verify it
      and extend it if not
    - re-resolve and re-check on every outbound call, not only at connect
      time (a hostname can be re-pointed after validation - DNS rebinding)
    - never follow redirects to a different host on a Jira API call
    - never echo the response body of an unexpected host back to the client

13.5 WEBHOOK VALIDATION
------------------------
  Covered in 6.4. The essentials restated as security requirements:
    - a 32-byte random secret per connection, in the URL
    - CONSTANT-TIME comparison (the timingSafeEqual pattern from
      functions/api/gbp/jobs.js:45-53). A naive === leaks the secret through
      timing given enough attempts.
    - no information in the 401 response body
    - unknown-issue events are accepted-and-dropped, not rejected, so the
      endpoint cannot be used to enumerate which issues SEOX tracks
    - the payload is data, never instruction: no value from it is used to
      pick a user, a project or a connection
    - rate limited per connection
    - the secret is rotatable without reconnecting (11.4)

13.6 CSRF
----------
  Not applicable to the SEOX API surface, because authentication is a Bearer
  token read from localStorage and attached explicitly by
  src/lib/authenticatedApiFetch.js - not a cookie. A cross-site form post
  carries no Authorization header. This is a property of the existing design
  and must not be changed (do not move the session to a cookie as part of
  this work).
  The webhook endpoint is not CSRF-relevant: it is unauthenticated by
  session and guarded by its own secret.

13.7 PERMISSIONS AND SCOPES
----------------------------
  - Within SEOX: any signed-in user may connect Jira for a project they own.
    No admin right is required, matching how Stripe and DeepSeek per-user
    settings already work. Only the admin_settings credential tabs require
    admin (assertAdmin in functions/api/settings/general.js:57).
  - Within Jira: the connected account needs Browse Projects, Create Issues,
    Add Comments and Transition Issues on the mapped project. The settings
    UI should state this, and the mapping validation should report which
    permission is missing when Jira returns 403 rather than a generic error.
  - SEOX must ask for no more than it uses. It does not need admin rights in
    Jira, and the docs must say so - a user who grants an admin token
    because SEOX was vague has been badly served.

13.8 AUDIT LOGGING
-------------------
  Every state-changing Jira action writes a jira_sync_logs row with
  actor_email, actor_kind, action, result and created_at (Section 20).
  Never logged, anywhere, in any form: the API token, the webhook secret,
  the Authorization header, or the encryption key. The existing code sets
  this standard explicitly (functions/_lib/admin-auth.js:11, app-settings.js
  "Never log the values themselves").

13.9 DISCONNECT BEHAVIOUR
--------------------------
  On disconnect:
    - api_token_encrypted, oauth_refresh_encrypted and
      webhook_secret_encrypted are set to NULL (not merely marked inactive -
      the secret must actually be gone)
    - status = 'disconnected'
    - jira_project_mappings.status = 'disabled'
    - all pending jira_jobs for the project are cancelled
    - jira_issue_links are RETAINED by default with state unchanged, so the
      history of what was filed survives. They stop syncing.
    - deleteLinks:true additionally deletes the link rows. The UI must
      confirm with the count, and state that Jira issues are NOT deleted.
    - SEOX does NOT delete the Jira webhook - it has no reliable way to know
      whether the user created it or someone else did. The UI tells the user
      to remove it in Jira, and the now-invalid secret makes it harmless
      regardless.
    - a jira_sync_logs row records who disconnected and when

13.10 CREDENTIAL ROTATION
--------------------------
  - Jira token: re-run connect with the new token. The row is updated in
    place, so mappings and links survive. No re-mapping required.
  - Webhook secret: 11.4, one click, with a warning that the old URL dies
    immediately.
  - JIRA_TOKEN_ENCRYPTION_KEY: rotating it invalidates every stored token.
    There is no re-encryption path in the MVP (GBP has the same limitation).
    The decrypt error message must therefore be actionable - "reconnect
    Jira" - which is what gbp-crypto.js already does. Document the key as
    permanent-until-planned-rotation in the runbook.
    [FUTURE] a dual-key re-encryption migration, if rotation becomes a
    requirement.

13.11 SENSITIVE DATA HANDLING
------------------------------
  Data flowing OUT of SEOX into Jira: URLs from the audited site, HTTP
  status codes, meta tag contents, and the finding description. All of it is
  public information about a public website. No SEOX user data, no other
  tenant's data, and no credentials leave.
  Data flowing IN from Jira: issue key, status, resolution, priority,
  assignee display name and accountId, and (if comment sync is on) comment
  text and author display name.
    - do NOT store Jira users' email addresses. Jira returns them on some
      endpoints; strip them before persisting or returning (11.9).
    - the trimmed webhook payload (12.5) exists partly for this reason.
    - comment text is third-party content: store it, render it as PLAIN TEXT
      only, never as HTML.
  Data residency: a Jira Cloud instance may be in a different region from
  the SEOX database. Worth a line in the user-facing documentation.

13.12 INPUT VALIDATION SUMMARY
-------------------------------
  baseUrl       https, public host, <= 1000 chars, no credentials in URL
  email         <= 255, basic shape check
  apiToken      <= 1024, never trimmed to a partial value, never logged
  projectId     must exist and be owned by the caller
  labels        Jira rejects labels containing spaces - slugify or reject
  summary       <= 255 after the [SEOX] prefix
  description   built server-side from structured input; a user-supplied
                override is accepted but size-capped
  findingType   <= 191 (it is indexed), charset-restricted to the slug set
  scope url     parsed with parsePublicHttpUrl before being stored or fetched
  linkId        integer, always queried WITH user_id
  all ids from Jira (project, issue type, priority, assignee) are validated
    against Jira itself before being saved, never trusted from the client


================================================================================
SECTION 14 - RELIABILITY AND FAULT TOLERANCE  [PROPOSED]
================================================================================

14.0 THE GOVERNING RULE
------------------------
Jira must not become a single point of failure for SEOX. Concretely, with
Jira completely unreachable:
  - every SEOX page renders
  - crawls start, run and complete
  - every audit and analysis tool works
  - findings are visible and exportable
  - the only visible difference is that Jira badges show "sync pending" and
    the settings panel shows the connection as unhealthy
This is enforced structurally by the rules in Section 15 (no SEO page may
await a Jira call) and by the failure handling below.

14.1 REQUEST TIMEOUTS
----------------------
  Every outbound Jira call goes through ONE client,
  functions/_lib/jira-client.js [PROPOSED], which mirrors
  functions/_lib/google-fetch.js:
    - AbortController with a default 15000 ms total timeout
    - 8000 ms for interactive calls made inside an HTTP request
      (connect, test, metadata) so a user is never left hanging
    - 30000 ms for background job calls, where latency is free
  Nothing calls fetch() to Jira directly. A single client is what makes the
  timeout, retry, rate-limit and logging behaviour uniform.

14.2 RETRIES AND BACKOFF
-------------------------
  RETRY (transient, the request did not reach Jira or Jira failed
  internally):
    - connect-level errors: the RETRYABLE_CODES set from google-fetch.js
      (ETIMEDOUT, ECONNRESET, ECONNREFUSED, ENETUNREACH, EHOSTUNREACH,
      EAI_AGAIN, ENOTFOUND, UND_ERR_CONNECT_TIMEOUT)
    - HTTP 502, 503, 504
    - HTTP 429 (special handling, 14.5)
  DO NOT RETRY (Jira has answered):
    - 400 bad request - the payload is wrong; retrying cannot fix it
    - 401/403 - credentials or permissions; a human must act
    - 404 - the project or issue is gone
    - 409/422 - a workflow or validation conflict
  In-request retries: 2, base delay 400 ms, exponential.
  Job-level retries: RETRY_BACKOFF_SECONDS [60, 300, 1800], max_attempts 3 -
  the exact values from functions/_lib/gbp-jobs.js:46, reused so operators
  only have one retry model to understand.

14.3 IDEMPOTENCY
-----------------
  Three layers, all of them database constraints rather than application
  checks:
    jira_issue_links.uq_jira_link_fingerprint   no duplicate issue per
                                                finding, ever
    jira_webhook_events.uq_jira_webhook_event   no duplicate event effect
    jira_jobs.uq_jira_jobs_idempotency          no duplicate queued work
  Plus the remote_updated_at ordering check (5.5) so a late duplicate cannot
  apply a stale value.
  ER_DUP_ENTRY is ALWAYS handled as success, never as an error - the rule
  established at functions/_lib/gbp-jobs.js:200-206 and 245-252.

14.4 SEOX-SIDE RATE LIMITING
-----------------------------
  The buckets listed in 11.0, via the existing
  functions/_lib/rate-limit.js consumeRateLimit(). They protect the shared
  Jira tenant allowance from one SEOX user, which is the same rationale the
  existing file states for GBP and WPScan.

14.5 JIRA-SIDE RATE LIMITING (429)
-----------------------------------
  Jira Cloud returns 429 with a Retry-After header (seconds) and sometimes
  X-RateLimit-Reset. Handling:
    - inside an HTTP request: do not retry. Return 429 to the caller with
      the Retry-After value so the UI can say "Jira is rate limiting us,
      try again in N seconds".
    - inside a job: reschedule the job for Retry-After seconds (clamped to
      [60, 3600]) WITHOUT incrementing attempts. A rate limit is not a
      failure and must not consume a retry - this is the trap that turns a
      brief throttle into a dead-lettered job. Note that gbp-jobs.js does
      increment attempts on a quota error; the Jira runner should improve on
      that rather than copy it.
    - record result='rate_limited' in jira_sync_logs so throttling is
      visible in the activity card.

14.6 BACKGROUND PROCESSING
---------------------------
  Everything that can wait, waits. Specifically these run as jobs, never
  inside a user's request:
    jira_verify       the post-resolution re-check (5.4)
    jira_reconcile    the periodic JQL sync (5.3)
    jira_webhook      webhook event application (6.7)
    jira_comment      posting a verification comment
    jira_transition   reopening an issue
    jira_auto_scan    evaluating auto-create rules after a crawl (18)
    jira_create       ONLY as a retry of a failed create, and for
                      auto-created issues. A manual create stays synchronous
                      because the user is watching and wants the issue key.
  Runner: functions/_lib/jira-jobs.js [PROPOSED], adapted from
  functions/_lib/gbp-jobs.js - same claim/complete/retry/dead-letter shape,
  same 15-minute stale-lock release, same unknown-job-type-goes-straight-to-
  dead-letter rule.

14.7 FAILED SYNC QUEUE, DEAD LETTERS AND RETRY UI
---------------------------------------------------
  - a job that exhausts max_attempts becomes status 'dead' with last_error
  - a dead job writes jira_sync_logs action='job.dead_letter', result='error'
  - the settings panel error card lists them with a [Retry] button
    (11.16 / 11.17), which resets the job to 'pending' with attempts=0
  - a link row whose create failed sits in state 'failed' and shows a
    [Retry] button on the finding itself, not only in settings - the user
    who tried to file it is the one who wants to know
  - counts of failed syncs feed the dashboard (Section 16)

14.8 CIRCUIT BREAKER
---------------------
  Worth it, and cheap, because the connection row already exists to hold the
  state:
    - 5 consecutive failures of kind 'connection' (not 4xx) on one
      connection -> jira_connections.status = 'error' and an
      open_until timestamp 5 minutes ahead (add a
      circuit_open_until datetime column to 12.1 if implementing this;
      otherwise encode it in status_detail - prefer the column)
    - while open, outbound calls for that connection fail fast without a
      network attempt, and jobs are rescheduled past open_until
    - one probe call is allowed after open_until (half-open); success closes
      the breaker and resets the counter
    - 401/403 do not trip the breaker - they set status='invalid_credentials'
      immediately, which is a different and permanent condition needing a
      human
  Rationale: without this, a Jira outage plus a large queue means thousands
  of 15-second timeouts, which will slow the single Node process that also
  serves the SEOX UI. That is the concrete mechanism by which Jira could
  degrade SEOX, and the breaker is what prevents it.

14.9 CONNECTION HEALTH
-----------------------
  Surfaced in three places: the settings connection card (9.3), the finding
  panel badge (Section 17), and the dashboard tile (Section 16). Driven by
  jira_connections.status, last_checked_at and last_event_at. Never inferred
  from the absence of errors - if it has not been checked, say so.

14.10 DEGRADED MODES - EXPLICIT BEHAVIOUR TABLE
-------------------------------------------------
  Jira unreachable          create returns 502 with a clear message; jobs
                            retry; SEOX otherwise unaffected
  Jira 401                  status='invalid_credentials'; creates are
                            blocked with "reconnect Jira"; no retry storm
  Jira 429                  14.5
  Webhook never configured  poll keeps everything correct, slower; the UI
                            says so
  Encryption key missing    connect returns a clear 500; existing links
                            still display (they hold no secrets); no crash
  Database down             the whole app is down anyway; nothing
                            Jira-specific
  DeepSeek down             AI enhancement silently falls back to the static
                            template (8.4)
  Target site unreachable
    during verification     retry, then leave in 'resolved_pending' with a
                            verification_error. NEVER reopen the ticket.

SECTION 15 - PERFORMANCE  [PROPOSED]
================================================================================

15.1 THE HARD RULES
--------------------
  R1  No SEO page may block its first render on a Jira API call.
  R2  No SEOX API endpoint that existed before this work may gain a Jira
      call in its request path.
  R3  No request to Jira is made while rendering a list; badges come from
      SEOX's own database.
  R4  Every Jira call inside an HTTP request has an 8-second ceiling (14.1).
  R5  Anything that can be a job, is a job (14.6).

R2 deserves emphasis. The tempting shortcut is to add Jira link counts to
the existing /api/auditor or /api/projects response. Do not. Those endpoints
are on the critical path of pages that must work with Jira down, and one
slow upstream call would make them all slow. Jira data is fetched
separately, in parallel, and is allowed to arrive late or not at all.

15.2 SEO PAGES MUST NOT DEPEND ON JIRA
----------------------------------------
  /auditor/issues renders entirely from the crawl state it already has.
  Jira link badges are a SECOND, independent fetch that populates when it
  returns. If it never returns, the page is still complete and correct -
  just without badges. Implemented as a separate useProjectData key so its
  loading and error state are isolated (this is exactly the property the
  store was designed for - see the comment at
  src/lib/projectDataStore.js:20-22: "Status and error live per entry, so a
  failed GSC fetch cannot take down the dashboard").

15.3 AVOIDING N+1 CALLS
------------------------
  The /auditor/issues page shows up to ~200 finding rows. Naively each row
  would ask "am I linked?" - 200 requests.
  Instead: ONE request per project fetches every link row for that project
  (11.13 without a fingerprint, which is a single indexed query on
  idx_jira_link_project_state), and the client builds a
  Map<fingerprint, link> once. Row badges are a map lookup.
  For the detail page, the same cached map answers the question with no
  request at all.
  The multi-fingerprint form of 11.13 exists for the case where a page
  needs a subset without loading everything.

15.4 CLIENT CACHING - REUSE, DO NOT INVENT
--------------------------------------------
  Use src/lib/projectDataStore.js via src/hooks/useProjectData.js, exactly
  as src/lib/gbpCache.js does. Proposed new module src/lib/jiraCache.js:

    export const JIRA_STATUS_KEY = 'jira:status';   staleTime  5 min
    export const JIRA_LINKS_KEY  = 'jira:links';    staleTime  2 min
    export const JIRA_META_KEY   = 'jira:meta';     staleTime 30 min
                                                    (projects/issue types/
                                                     priorities - settings
                                                     page only)

  This gives single-flight, per-key subscriptions and shared state across
  every screen for free, and it is the pattern the codebase already proved
  out (the gbpCache.js header documents the measured before/after:
  "POST /api/gbp/connect four times and GET /api/gbp/locations five times,
  for data that had not changed").

  Invalidate JIRA_LINKS_KEY after create, unlink, retry and sync-now.

15.5 SERVER CACHING
--------------------
  Jira metadata (projects, issue types, priorities, components) is cached
  per connection in process memory for 10-30 minutes, following the
  app-settings.js cache shape. These lists change rarely and the settings
  page hits them on every open.
  Issue state is NOT cached beyond the link row - the link row IS the cache,
  refreshed by webhook and poll.

15.6 AVOIDING DUPLICATE JIRA API CALLS
----------------------------------------
  - the reconcile poll is ONE JQL search per project per cycle, not one
    call per issue (5.3). This is the single most important performance
    decision in the design: it makes cost O(projects) rather than
    O(linked findings).
  - the pre-flight duplicate JQL search (4.4 step 5) runs only when no local
    link row exists - the common case skips it entirely.
  - the metadata cache prevents the settings page re-fetching project lists.
  - a webhook event makes the next poll a no-op for that issue, because
    remote_updated_at already matches.

15.7 BUNDLE SIZE
-----------------
  - JiraPanel.jsx is loaded with the settings page, which is already lazy
    (src/App.jsx:66).
  - The finding-panel Jira component must be lazy too, or code-split with
    the auditor chunk - it must not enter the entry chunk. The project has a
    600 KB chunkSizeWarningLimit and a documented history of the eager
    payload regressing to 1.8 MB (vite.config.js build comment).
  - NO new npm dependency. No Jira SDK, no HTTP client library. fetch() plus
    the existing helpers is sufficient; the Atlassian JS SDK is large and
    unnecessary for the handful of endpoints used.

15.8 DATABASE PERFORMANCE
--------------------------
  Every hot query is index-covered by design:
    link list for a project      idx_jira_link_project_state
    webhook issue resolution     idx_jira_link_issue_lookup
    duplicate check              uq_jira_link_fingerprint
    job claim                    idx_jira_jobs_claim
    activity list                idx_jira_sync_logs_project
  The two high-volume tables (jira_sync_logs, jira_webhook_events) have
  mandatory retention (12.4, 12.5). Without pruning they would eventually
  dominate the database - this project has already been bitten by a
  size-related MySQL problem (SORT_BUFFER_FIX.md in the repository root).

15.9 NO REDUX - CONCLUSION
---------------------------
  Analysis outcome: Redux is NOT required and must not be introduced.
  Reasons, in order of weight:
    1. The Jira state is per-project server state with a cache, not shared
       client state. projectDataStore + useProjectData already models
       exactly that, with single-flight and per-key subscriptions.
    2. The codebase has an explicit, commented decision against it
       (src/hooks/useProjectData.js:14-19).
    3. Adding a store would create a second state paradigm for one feature,
       which is precisely the duplicate-logic outcome the brief forbids.
    4. It would add bundle weight to an app that has measurably fought for
       its entry-chunk size.

SECTION 18 - AUTOMATION OPPORTUNITIES  [PROPOSED - phase 4]
================================================================================

18.0 THE OVER-AUTOMATION RISK, STATED PLAINLY
-----------------------------------------------
A first crawl of a neglected 2,000-page site can produce several thousand
findings across 15 categories. Automatic creation without hard limits would
file hundreds of Jira issues into a client's board in one run. That outcome
is not a bug to fix later - it is a relationship-ending event, and the team
would disable the integration permanently.

Therefore automation ships with these invariants, none of them optional:
  - auto_create_enabled defaults to FALSE (10.7)
  - maxPerRun default 10, hard ceiling 50
  - maxPerDay default 25, hard ceiling 100
  - error severity only, by default
  - an explicit allow-list of finding types; there is no "all findings"
    setting
  - minOccurrences: a finding must appear in 2 consecutive crawls before it
    qualifies, which filters transient failures (a 500 during a deploy, a
    timeout on a slow page)
  - every automatic creation passes through the same fingerprint duplicate
    check as a manual one
  - the enabling modal states the current qualifying count before the user
    confirms

18.1 TRIGGER POINTS
--------------------
  T1  Crawl completed. The browser finishes a crawl and posts the finding
      summary; the server enqueues 'jira_auto_scan'.
      NOTE the constraint from 2.9: the crawl runs in the browser, so the
      server only learns about findings when the browser tells it. The
      existing saveProjectData(key:"auditor") write
      (src/context/CrawlContext.jsx:640-650) is the natural hook - the
      auto-scan job can read the same stored payload rather than needing a
      new client call.
  T2  A tool result is saved (speed, wpscan, robots) - the saveToolResult
      path in functions/api/projects.js.
  T3  A webhook-driven recurrence (reopenBehaviour handling, 4.4).
  T4  Scheduled daily sweep, as a backstop for T1/T2 misses. Low priority.

18.2 RECOMMENDED AUTOMATION (ship in phase 4)
-----------------------------------------------
  A1  Critical technical SEO errors
      Trigger      jira_auto_scan after a crawl
      Conditions   severity='error' AND finding_type IN
                   ('404-page','5xx-page','4xx-page','timed-out',
                    'redirect-loop','broken-redirect',
                    'redirect-chain-too-long')
                   AND seen in 2 consecutive crawls
                   AND the URL is internal and indexable
      Duplicates   fingerprint check (4.4)
      Priority     from severityPriorityMap ('error' -> High)
      Assignee     mapping default (usually none)
      Labels       seox, seox-auditor, seox-error, seox-auto
      Notify       in-app only (Section 19)
      Reopen       per reopenBehaviour
      Cap          maxPerRun / maxPerDay

  A2  Indexability breakage
      Conditions   finding_type IN ('canonical-points-to-4xx',
                   'canonical-points-to-5xx','canonical-points-to-redirect',
                   'noindex-page-sitemap','3xx-redirect-sitemap')
      Rationale    each is unambiguous and unintentional. Note that plain
                   'noindex-page' and 'nofollow-page' are EXCLUDED - they are
                   very often deliberate, and auto-filing them would be the
                   fastest way to lose the team's trust.

  A3  Critical WordPress security findings
      Trigger      a wp_security_scans row completes
      Conditions   severity IN ('critical','high') AND confirmed = 1
      Priority     Highest / High
      Labels       seox, seox-security, seox-auto
      Rationale    a confirmed CVE with a known fixed_in version is the
                   least ambiguous ticket SEOX can produce.
      [CONFIRM]    possibly a different Jira project (3.10)

  A4  Sitemap defects
      Conditions   the two error-severity sitemap findings (3.3)
      Rationale    a sitemap listing noindex or redirecting URLs is always a
                   defect, and always cheap to fix.

18.3 OPTIONAL AUTOMATION (opt-in, off by default, phase 4+)
-------------------------------------------------------------
  O1  Core Web Vitals threshold breach
      Conditions   a user-set threshold (e.g. mobile LCP > 4.0s) breached in
                   2 consecutive runs, on a user-designated key-page list
      Why optional Lighthouse is noisy run to run; a single-run trigger
                   would produce flapping tickets. Requires the key-page
                   list, which does not exist yet.
  O2  New broken internal link
      Conditions   a link target that returned 200 in the previous crawl now
                   returns 4xx/5xx - a regression, not a backlog item
      Why optional needs crawl-over-crawl diffing, which the client-side
                   crawl state supports but the server does not yet.
  O3  Batch content issue
      Conditions   more than N pages missing a title or meta description ->
                   ONE batched issue (4.6)
      Why optional teams differ wildly on whether content work belongs on
                   the dev board.
  O4  Critical GSC issue
      Why optional see 3.11. Recommended as [FUTURE], not phase 4.
  O5  Important GBP finding
      Why optional see 3.13. Narrow subset only, and GBP is quota-blocked.
  O6  Content optimization recommendation
      Why optional it is a brief, not a defect (3.14).

18.4 WHAT MUST NEVER BE AUTOMATED
-----------------------------------
  - robots.txt changes (3.2) - too high a blast radius to file unattended
  - anything at 'notice' severity
  - E-E-A-T findings (3.5) - editorial, not developer work
  - keyword opportunities (3.18) - no definite done state
  - one issue per URL fan-out (4.6)
  - AI-generated descriptions in the automatic path (8.4)

18.5 THE AUTO-SCAN JOB
-----------------------
  jira_auto_scan pseudocode:
    load the mapping; exit if !auto_create_enabled or status != 'active'
    load auto_create_rules
    load the stored finding set for the project
    load the previous crawl's finding set (for minOccurrences)
    candidates = findings matching severity/module/type rules
                 AND present in both crawls
                 AND not already fingerprinted in jira_issue_links
    check the daily counter (count of creation_mode='auto' links created
      in the last 24h); trim candidates to the remaining allowance
    sort by severity then by affected_url_count descending
    take maxPerRun
    for each: enqueue a jira_create job (not inline - one Jira failure must
      not abort the batch)
    write a jira_sync_logs row summarising: considered, qualified, created,
      skipped-duplicate, skipped-cap
  The summary row matters: when a user asks "why didn't SEOX file X", the
  answer must be in the activity log.

18.6 NOTIFICATION AND VISIBILITY
----------------------------------
  Every automatic creation is visible in the activity card and carries
  creation_mode='auto' plus the seox-auto label in Jira, so a team can
  always tell a robot's ticket from a human's, and can JQL them separately.

SECTION 19 - NOTIFICATIONS  [PROPOSED]

19.1 WHAT ALREADY EXISTS - AND WHAT DOES NOT
----------------------------------------------
From 2.17, verified: there is NO toast library, NO global notification
context, and NO email-sending code anywhere in the repository. The only
persisted alert mechanism is gbp_job_alerts surfaced at /gbp/operations, and
user_projects.notify_email is a stored flag with no consumer.

This plan therefore does NOT propose email notifications, and does not
pretend an infrastructure exists that does not. Doing so would be the
easiest way to produce a plan that cannot be implemented as written.

19.2 IN-APP NOTIFICATION - WHAT TO BUILD
------------------------------------------

    Connection test result    inline in the settings card
  This requires no new infrastructure - it is local component state, which
  is how every other action in SEOX already reports itself.

  Tier 2 - persistent, surfaced where the user will look
    Status changed            the badge and panel simply show the new state
                              on next view. No alert. A status change is
                              expected and constant; alerting on it would be
                              noise.
    Verification succeeded    the panel shows 'verified' and the dashboard
                              "Verified fixes" count increments
    Verification FAILED       this one deserves prominence: it is news. Show
                              it as a counted badge on the dashboard Jira
                              card ("2 issues reopened after verification")
                              and in the reopened state on the finding.
    Sync failures             counted in the settings error card and on the
                              dashboard card when non-zero

  Event                       In-app  Dashboard  Activity log  Email

19.4 EMAIL  [FUTURE]
---------------------
Recommended future work, and explicitly out of scope here:
  - a shared notification service with an email transport
  - honouring users.notification_preferences and
    user_projects.notify_email, both of which already exist unused
  - a digest rather than per-event mail (per-event mail on a busy project
    is unusable)
  This should be built once, for the whole product, not for Jira alone.
  Building a Jira-only mailer would be exactly the duplicate infrastructure

19.5 NOT RECOMMENDED

  - Slack/Teams webhooks: interesting, but that is a second integration, and

    duplicating Jira's notifications would annoy the team.

22.3 SEO VERIFICATION
----------------------
  jira_verify job becomes due
    |
    v
  functions/_lib/jira-verify.js
    |  load the link row + verification_spec
    |  spec.kind === 'manual' -> seox_state='verified', log, done
    v
  parsePublicHttpUrl(spec.url)     [functions/_lib/url-security.js]
    |  private/invalid -> fail closed, log, do NOT reopen
    v
  fetch the URL through the existing crawler fetch path
    |  network failure -> retry per backoff
    |  after max attempts -> stay 'resolved_pending',
    |                        verification_error set, surfaced in the UI
    v
  run spec.checks against the response
    |
    +-- all pass
    |     UPDATE seox_state='verified', verified_at, verification_result
    |     if post_verification_comments:
    |         enqueue 'jira_comment' -> POST /rest/api/3/comment
    |         "SEOX re-checked <url> on <date> and this issue is fixed."
    |     INSERT jira_sync_logs 'verify.run' success
    |     -> dashboard "Verified fixes" +1
    |
    +-- any fail
          UPDATE seox_state='reopened', reopened_count+1,
                 verification_result = the failing checks
          enqueue 'jira_comment' with the specific failure
          reopen_behaviour:
            'reopen'  -> enqueue 'jira_transition' to an open status;
                         if no valid transition, fall back to comment-only
                         and record that
            'comment' -> comment only
            'none'    -> leave the Jira issue closed; SEOX shows 'reopened'
          INSERT jira_sync_logs 'verify.run' error

22.4 FAILURE HANDLING
----------------------
  SEOX action needing Jira
    |
    v
  functions/_lib/jira-client.js
    |
    +-- success -> done
    |
    +-- 4xx (not 429)  -> permanent. state='failed', log, surface to the
    |                     user with the Jira message. NO retry.
    |
    +-- 429            -> read Retry-After
    |                     in-request: return 429 upward with the delay
    |                     in-job:     reschedule run_after = now + delay,
    |                                 DO NOT increment attempts
    |                     log result='rate_limited'
    |
    +-- 5xx / connect error / timeout
          in-request: 2 quick retries (400ms base); then fail and enqueue
          in-job:     attempts+1
                        attempts < max_attempts
                          -> retryJob(RETRY_BACKOFF_SECONDS[attempts-1])
                             i.e. 60s, then 300s, then 1800s
                        attempts >= max_attempts
                          -> deadLetterJob(last_error)
                             jira_sync_logs 'job.dead_letter'
                             surfaced in the settings error card
                             [Retry] resets status='pending', attempts=0
          5 consecutive connect failures on one connection
                          -> circuit breaker opens for 5 minutes (14.8);
                             calls fail fast; jobs reschedule past it;
                             one half-open probe closes it on success

SECTION 24 - TESTING STRATEGY  [PROPOSED]
================================================================================

Runner: node --test (2.20). Handlers are tested by calling onRequest
directly with a Request and a stub env - no HTTP server, no Jira. Outbound
Jira calls are faked by injecting a fetch implementation into
jira-client.js (the client must therefore accept an injectable fetch, which
is the main testability requirement on its design).

24.1 AUTHENTICATION
--------------------
  [ ] valid credentials: connect succeeds, the row is written, the token
      column is not plaintext
  [ ] invalid credentials: Jira 401 -> SEOX 401, no row written
  [ ] Jira 403 (valid token, no permission) -> a distinct, actionable
      message, not "unauthorized"
  [ ] missing credentials: 400 naming the missing field
  [ ] expired/revoked token on a later call -> status becomes
      'invalid_credentials', no retry storm, the UI says reconnect
  [ ] no SEOX session -> 401 before any database or Jira access
  [ ] auth database unreachable -> 503, NOT 401 (preserving
      auth-token.js:44-52)
  [ ] a user cannot connect Jira for a project they do not own -> 403

24.2 JIRA CONNECTION
---------------------
  [ ] successful connection stores base_url normalised (trailing slash and
      /rest suffix stripped)
  [ ] Jira unreachable (connect timeout) -> 502/504 with a clear message,
      status='error', nothing persisted as connected
  [ ] invalid base URL: not a URL, http on a public host, a private IP,
      169.254.169.254, a URL with embedded credentials -> all 400
  [ ] a redirect to a different host during a Jira call is not followed
  [ ] test-connection updates last_checked_at and returns ok:false rather
      than an HTTP error when the credential is bad
  [ ] disconnect nulls all three encrypted columns and retains links
  [ ] disconnect with deleteLinks:true removes links and says how many

24.3 ISSUE CREATION
--------------------
  [ ] successful creation: 201, the link row is 'linked', the key is
      returned, a sync log row exists
  [ ] duplicate prevention: a second identical create returns 200
      alreadyLinked and makes NO Jira call
  [ ] concurrent creates: two simultaneous identical requests produce
      exactly one Jira call and one link row (simulate the ER_DUP_ENTRY
      path directly)
  [ ] fingerprint stability: the same finding from the auditor and from the
      on-page analyzer produces ONE link (3.21)
  [ ] fingerprint sensitivity: a different URL, a different finding type or
      a different project produces a different fingerprint
  [ ] URL normalisation: trailing slash, fragment and case differences
      collapse to one fingerprint
  [ ] invalid payload: missing findingType, missing scope -> 400
  [ ] no mapping -> 409 with an actionable message
  [ ] Jira 400 with a field error -> the field error reaches the user
      verbatim
  [ ] Jira 5xx -> the link is 'failed' and a retry job is queued
  [ ] summary truncation at 255 including the [SEOX] prefix
  [ ] the URL list caps at 50 and states the true total
  [ ] the 'seox' label is always present and cannot be removed by overrides

24.4 SYNCHRONISATION
---------------------
  [ ] Jira -> SEOX: each statusCategory maps to the right seox_state
  [ ] resolution 'Won't Do' -> wont_fix and NO verification is scheduled

25.0 WHAT THE REPOSITORY DOES AND DOES NOT CONTAIN - STATED HONESTLY
----------------------------------------------------------------------
The brief says "do not assume the architecture; inspect the actual server
configuration first". The repository was searched for it and it is NOT
present:

  Searched for nginx | pm2 | 4173 across *.md, *.txt, *.conf, *.json,
  *.js, *.jsonc. The only matches are package.json, vite.config.js, three
  test files and build artefacts under .wrangler/ and dist/.
  There is NO nginx.conf, NO ecosystem.config.js, NO pm2 file, NO
  Dockerfile, NO systemd unit, NO deploy script in this repository.

Therefore this section documents (a) what IS verifiable from the code, and
(b) exactly what must be inspected ON THE SERVER before deployment, as a
checklist. It does not invent a configuration.

25.1 VERIFIED FROM THE CODE  [EXISTING]
-----------------------------------------
  Frontend + API process
    package.json "preview": "vite preview --host 0.0.0.0 --port 4173"
    vite.config.js preview: { host: true, port: 4173 }
    vite.config.js server:  { port: 3000, host: true }        (dev only)
  The SAME Node process serves the built SPA from dist/ and every /api/*
  route, via the ~57 Connect middlewares registered by the plugins
  (2.5). There is no separate API server. There is no Express app in the
  request path (server/project-details-api.js is an optional adapter that
  nothing in this deployment uses).

  Build
    npm run build -> vite build -> dist/

  Database
    MySQL, reached with mysql2 using MYSQL_HOST/PORT/USER/PASSWORD/DATABASE
    from the process environment, .env or .dev.vars (loadDevApiEnv,
    vite.config.js:125). Pool size 10.

  Environment loading - IMPORTANT
    Vite does NOT copy .env into process.env. The API middlewares call
    loadDevApiEnv() per request, which merges process.env, Vite's loadEnv,
    .env and .dev.vars. So a variable placed in .env on the server IS
    visible to the API handlers even though process.env does not have it.
    Any new Jira variable must be readable through env, which it will be
    if every handler takes env from onRequest({ request, env }) - as they
    all do. Do not read process.env directly in new Jira code.

  Known production host characteristics (from
  functions/_lib/google-fetch.js, which documents a real incident):
    - no global IPv6 address; only a link-local fe80::/10 on ens160
    - ~324 ms RTT to oauth2.googleapis.com, versus Node's 250 ms
      autoSelectFamilyAttemptTimeout default
    - outbound HTTPS to third parties therefore NEEDS an explicit timeout
      and retry, which is precisely why jira-client.js is specified the way
      it is (14.1/14.2). This is not defensive over-engineering; it is a
      documented property of this host.

-----------------------------------------------

25.4 WHAT CHANGES FOR JIRA - INFRASTRUCTURE SIDE
--------------------------------------------------
  Nginx
    Probably NOTHING, if /api/ already proxies to :4173 as a prefix. Verify
    with 25.2. If routes are enumerated individually in the config, add:
        location /api/jira/ { proxy_pass http://127.0.0.1:4173; ... }
    Check that the webhook path is not stripped of its query string - the
    secret travels in ?t=, so any config that drops or rewrites the query
    breaks authentication silently.
  Firewall
    Outbound 443 to the Jira host must be allowed.
    Inbound 443 to /api/jira/webhook must be reachable from Atlassian's
    egress ranges. Atlassian publishes those ranges; whether to allow-list
    them is a judgement call - the URL secret is the real control, and an
    IP allow-list that goes stale silently breaks sync.
  TLS
    No change. The webhook requires a valid publicly trusted certificate;
    Atlassian will not deliver to a self-signed endpoint.
  CORS
    No change is needed. The browser calls only same-origin /api/* paths,
    and all Jira traffic is server-to-server. The existing corsHeaders()
    "*" policy is inherited; note that it is safe here only because
    authentication is a Bearer token, not a cookie (13.6).

25.5 THE MULTI-INSTANCE QUESTION  [CONFIRM - important]
---------------------------------------------------------
  If PM2 runs the app in cluster mode with more than one instance, several
  designs in this plan need a second look:
    - the job runner's claim uses a lock_token and a locked_at, which IS
      safe across processes (that is why gbp-jobs.js works that way) - fine
    - the in-process metadata cache (15.5) would be per-instance, which is
      harmless (just fewer cache hits)
    - the app-settings cache is already per-process today, so this is a
      pre-existing, accepted condition
    - the circuit breaker (14.8) would be per-instance unless its state is
      the database column, which is why 14.8 specifies a column rather than
      a module-level variable
  If instances > 1, also confirm that only ONE of them receives the
  scheduler POST, or that the claim logic is genuinely relied upon (it is).

25.6 DEPLOYMENT SEQUENCE
--------------------------
  1. On a staging copy (or a maintenance window):
     a. back up the production database
     b. run migration/mysql/20261001_jira_integration.sql and verify the
        six tables exist with the expected indexes
  2. Add the new environment variables (Section 26) wherever the process
     actually reads them (25.2), including
     JIRA_TOKEN_ENCRYPTION_KEY - generate with: openssl rand -base64 32
  3. Deploy the code; npm ci; npm run build
  4. Restart the process (pm2 restart <app> / systemctl restart <unit>)
  5. Smoke test, in this order:
     a. an existing page still works (regression first, always)
     b. GET /api/jira/status?projectId=<known> returns
        {"connected":false} with 200 - this proves the route is mounted in
        PREVIEW, which is the failure mode this project is prone to
     c. connect a sandbox Jira; test the connection
     d. map a project; create one issue from a real finding
     e. transition it in Jira; confirm the webhook arrives (check
        jira_webhook_events) and the state moves
     f. confirm verification runs and writes a result
  6. Register the Jira webhook using the URL from the settings panel
  7. Enable the job trigger (25.7)
  8. Watch jira_sync_logs for the first 24 hours

25.7 THE JOB TRIGGER  [CONFIRM]
---------------------------------
  Jobs need something to call POST /api/jira/jobs on a timer. Three
  options, in order of preference for THIS deployment:

  (A) A system cron entry on the application host. Simplest, no external
      dependency, and the host already runs the app:
        */2 * * * * curl -fsS -m 60 -X POST \
            -H "X-Jira-Scheduler-Token: $JIRA_SCHEDULER_TOKEN" \
            -H "Content-Type: application/json" -d '{"trigger":"cron"}' \
            http://127.0.0.1:4173/api/jira/jobs >/dev/null
      Note it calls 127.0.0.1 directly, bypassing nginx and the public
      internet. Every two minutes is a reasonable cadence given the
      verification delay is measured in minutes.
  (B) The Cloudflare scheduler worker pattern
      (seox-main/worker/gbp-scheduler/). Correct if that worker is in fact
      deployed and used; pointless overhead if it is not.
  (C) A systemd timer. Equivalent to (A) with better logging.

  Whichever is chosen, it must NOT be a setInterval inside the app process:
  that breaks under multi-instance, gives no visibility, and dies silently
  with the process. It also has no place in a Vite preview server.

  [CONFIRM] Determine how GBP jobs are currently triggered in production -
  the same mechanism should drive Jira, and if GBP jobs are NOT currently
  being triggered at all (GBP_SCHEDULER_TOKEN is absent from the local .env,
  which is a hint worth chasing), that is a pre-existing finding worth
  reporting separately.

25.8 ROLLBACK
--------------
  - Application: redeploy the previous build and restart. The Jira tables
    become inert; nothing else reads them.
  - Database: the migration only adds tables. Rolling back the code needs
    NO database rollback. If the tables must go, DROP the six; no existing
    data is affected.
  - Webhook: delete it in Jira, or simply leave it - a 404 from a rolled-
    back deployment is harmless, and Jira will stop retrying.
  This clean rollback story is a direct consequence of the additive-only
  schema decision in 12.8.

25.9 MONITORING AFTER DEPLOYMENT
----------------------------------
  - jira_sync_logs WHERE result='error' in the last hour
  - jira_jobs WHERE status='dead'
  - jira_webhook_events WHERE status='pending' AND received_at < now-15min
    (the drain is not running)
  - jira_connections WHERE status != 'connected'
  - process memory and event-loop lag after enabling jobs (the drain shares
    the process that serves the UI)

26.1 NEW VARIABLES

  JIRA_TOKEN_ENCRYPTION_KEY        REQUIRED

    webhook_secret_encrypted. Losing or changing it invalidates every

  JIRA_SCHEDULER_TOKEN             REQUIRED for background jobs

    X-Jira-Scheduler-Token header on POST /api/jira/jobs. If unset, the

    functions/api/gbp/jobs.js:57-60.
    [CONFIRM] alternative: reuse GBP_SCHEDULER_TOKEN with a single drain
    endpoint (11.19).

  APP_URL                          EXISTING - must be correct
    Already in .env and .env.local. Used to build the webhook URL shown in
    the settings panel. If it is wrong, users register an unreachable
    webhook and sync silently falls back to polling. Verify its production
    value as part of 25.2.

26.2 OPTIONAL VARIABLES
------------------------
  JIRA_WEBHOOK_SECRET
    A global shared secret additionally required as the
    X-SEOX-Webhook-Secret header (6.4b). Only useful where a proxy can

    "true" permits http:// and private hosts as a Jira base URL, for

  JIRA_DEFAULT_TIMEOUT_MS          default 15000
  JIRA_INTERACTIVE_TIMEOUT_MS      default 8000
  JIRA_MAX_RETRIES                 default 2
    Tuning knobs matching google-fetch.js's constants. Given the documented
    latency characteristics of this host (25.1), being able to raise the

SECTION 27 - BACKWARD COMPATIBILITY
================================================================================

27.1 THE REQUIREMENT
---------------------
Jira is an additional integration, never a dependency. With Jira not
configured, not connected, or unreachable, SEOX behaves exactly as it does
today.

27.2 HOW THE DESIGN GUARANTEES IT - MECHANISM BY MECHANISM
------------------------------------------------------------
  Additive schema only (12.8). No existing table is altered, so no existing
    query changes plan, and no existing write can fail because of Jira.
  New routes only (23.2). Every Jira endpoint is a new path. No existing
    handler is edited except vite.config.js's plugin list, which is
    additive.
  Separate data keys (15.4). Jira client state lives in its own
    projectDataStore keys, whose loading and error state cannot affect
    another key - the property the store was explicitly built for.
  Render-nothing-when-absent (17.2, 16.2). The UI shows no Jira affordance
    at all when there is no connection, rather than a disabled one.
  No shared request path (15.1 R2). No pre-existing endpoint gains a Jira
    call.
  Optional environment (26.5). A missing encryption key degrades Jira, not
    the app.
  Optional jobs. If the drain never runs, nothing else is affected; only
    Jira sync lags.

27.3 EXPLICIT COMPATIBILITY ASSERTIONS
----------------------------------------
  With Jira absent, all of these MUST hold and are covered by 24.7:
  [ ] existing SEOX features work unchanged
  [ ] existing SEO APIs return identical responses
  [ ] existing SEO pages render identically
  [ ] existing projects load and save unchanged
  [ ] crawls run, persist and report unchanged
  [ ] AI features work unchanged
  [ ] settings pages work; the Jira tab exists but is inert
  [ ] GBP, GSC, Stripe, WPScan and DeepSeek integrations are untouched
  [ ] the built bundle grows only by the lazy Jira chunks

27.4 THINGS THAT WOULD BREAK THIS - DO NOT DO THEM
----------------------------------------------------
  - adding a Jira count to the /api/projects or /api/auditor response
  - making the auditor page await a Jira fetch before first paint
  - throwing at module load when a Jira env var is missing
  - adding a NOT NULL column to an existing table
  - putting Jira state into CrawlContext or ProjectsContext
  - making the job drain a hard dependency of any existing flow
  - eager-importing the Jira panel into the entry chunk


================================================================================
SECTION 28 - RISKS AND MITIGATIONS
================================================================================

R1  JIRA API RATE LIMITS
    Risk        A large auto-create run or a wide reconcile exhausts the
                tenant's allowance; Jira throttles SEOX and, worse, other
                tools the customer uses.
    Likelihood  Medium.   Impact  Medium.
    Mitigation  One JQL search per project per cycle rather than per issue
                (5.3); SEOX-side buckets (11.0); honour Retry-After without
                consuming a retry (14.5); hard per-run and per-day
                auto-create caps (18.0); server-side metadata caching.

R2  AUTHENTICATION EXPIRY / REVOCATION
    Risk        A revoked or rotated token silently stops all sync.
    Likelihood  Medium.   Impact  Medium.
    Mitigation  401/403 sets status='invalid_credentials' immediately and
                stops retrying; the settings card, dashboard card and
                finding panel all show it; a periodic test-connection keeps
                last_checked_at fresh so "it worked yesterday" is visible.
                Re-connecting updates the row in place, so no mapping or
                link is lost.

R3  WEBHOOK FAILURES
    Risk        Events lost during a deploy, an outage, or because the
                webhook was never registered; SEOX shows stale statuses.
    Likelihood  High - this WILL happen.   Impact  Low, by design.
    Mitigation  The reconcile poll is a floor, not an optimisation (5.3),
                with a deliberate window overlap; webhook health is
                surfaced honestly (6.9); the durable event inbox allows
                replay (6.7).

R4  DUPLICATE ISSUE CREATION
    Risk        Two Jira issues for one finding; the board loses
                credibility.
    Likelihood  Medium without care.   Impact  High - this is the failure
                users notice and complain about first.
    Mitigation  A database UNIQUE index on (user_id, fingerprint), not an
                application check (4.4); ER_DUP_ENTRY handled as success;
                a pre-flight JQL adoption search; a shared fingerprint
                namespace so the auditor, on-page analyzer and Screaming
                Frog import collapse (3.21, 3.22); a dedicated concurrency
                test (24.3).

R5  DATA SYNCHRONISATION CONFLICTS / OUT-OF-ORDER EVENTS
    Risk        A stale webhook overwrites a newer state.
    Likelihood  Medium.   Impact  Medium.
    Mitigation  remote_updated_at ordering check on every apply (5.5);
                clear ownership of each fact (Jira owns workflow, SEOX owns
                whether the problem exists); 'reopened' models the genuine
                disagreement rather than hiding it.

R6  JIRA DOWNTIME
    Risk        Jira is unavailable for hours.
    Likelihood  Low-Medium.   Impact  Low, by design.
    Mitigation  Section 14 in full: timeouts, bounded retries, the job
                queue, and the circuit breaker that prevents thousands of
                15-second timeouts from degrading the single Node process
                that also serves the UI (14.8). Core SEOX is untouched
                (Section 27).

R7  LARGE NUMBERS OF SEO FINDINGS
    Risk        A 5,000-page crawl produces thousands of findings; a user
                bulk-files them and destroys a Jira board.
    Likelihood  High if unguarded.   Impact  Very high - relationship-level.
    Mitigation  Auto-create off by default with per-run/per-day caps and an
                allow-list (18.0); no per-URL fan-out (4.6); batched issues
                instead; the enabling modal states the qualifying count;
                the URL list inside an issue capped at 50 (4.3).

R8  LONG-RUNNING SYNCHRONISATION
    Risk        A reconcile or verification run blocks the event loop of
                the process that serves the UI.
    Likelihood  Medium.   Impact  Medium.
    Mitigation  Bounded batch sizes (10 jobs per drain, 100 JQL results per
                page); timeouts on every outbound call; the drain is called
                on a timer rather than run inline; monitor event-loop lag
                after enabling (25.9).

R9  CREDENTIAL SECURITY
    Risk        A Jira token leaks through a response, a log or the bundle.
    Likelihood  Low with discipline.   Impact  Very high.
    Mitigation  AES-GCM at rest (13.1); never returned to the browser
                (13.2); never logged (13.8, 20.4); no VITE_ prefixed Jira
                variable (26.3); explicit tests that walk every response
                body and captured log line (24.6).

R10 SSRF VIA THE USER-SUPPLIED BASE URL
    Risk        A crafted base URL makes the server call internal services
                or a cloud metadata endpoint.
    Likelihood  Medium.   Impact  Very high.
    Mitigation  parsePublicHttpUrl from the existing url-security.js;
                https-only; re-validate on every call, not just at connect
                (DNS rebinding); no cross-host redirect following; never
                echo an unexpected response body (13.4).

R11 JIRA API VERSION CHANGES
    Risk        Atlassian deprecates an endpoint or changes ADF.
    Likelihood  Low-Medium over years.   Impact  Medium.
    Mitigation  All Jira access behind one client and one issue builder
                (23.1), so a version change is a small, localised edit;
                pin to REST v3 explicitly; a connection test that exercises
                the real endpoints so breakage surfaces as an unhealthy
                connection rather than a silent failure.

R12 PERFORMANCE IMPACT ON SEOX
    Risk        Jira work slows the shared Node process.
    Likelihood  Medium.   Impact  Medium.
    Mitigation  Section 15's hard rules; no Jira call on any pre-existing
                request path; one link query per page, not per row; the
                circuit breaker; bounded job batches.

R13 THE VITE PREVIEW REGISTRATION TRAP
    Risk        A route registered only for configureServer works in dev
                and 404s on :4173. Every Jira feature appears broken in
                production only.
    Likelihood  High - this project has already been bitten by it, which is
                why the comment and the test exist.
    Impact      High.
    Mitigation  The 24.8 preview-mount test, written BEFORE the routes; the
                registration pattern copied verbatim from GBP_ROUTES; a
                smoke test at deploy that hits /api/jira/status on :4173
                (25.6 step 5b).

R14 THE DUPLICATE REPOSITORY / MIGRATION DIRECTORY
    Risk        The Jira migration is written into the directory that is
                not actually deployed, and the tables never exist in
                production.
    Likelihood  Medium - the GBP migrations are already only in seox-main/.
    Impact      High.
    Mitigation  Phase 0 resolves it before any other work (2.2a, 21).

R15 VERIFICATION FALSE POSITIVES
    Risk        SEOX declares a finding "verified" when it is not fixed
                (for example, it fetched a cached page), or reopens a
                ticket wrongly.
    Likelihood  Medium.   Impact  Medium - a false "verified" is worse than
                no verification, because it is a confident wrong answer.
    Mitigation  A configurable delay before checking (10.13); cache-busting
                request headers on the verification fetch; a fetch failure
                NEVER reopens a ticket (5.4); the specific failing check is
                quoted in the Jira comment so a human can judge; 'manual'
                specs are honest about what cannot be checked.

R16 SCOPE CREEP INTO A TASK MANAGER
    Risk        SEOX gradually grows assignees, due dates and boards.
    Likelihood  Medium over time.   Impact  Medium.
    Mitigation  The responsibility split in 1.3 and 31; the explicit rule
                that SEOX never changes assignee, priority or sprint (5.2);
                the rejected-settings list in Section 10.

SECTION 29 - RECOMMENDED MVP SCOPE

29.1 THE MVP  (Phases 0-3)
----------------------------
The smallest thing that delivers the whole value proposition. All ten items
from the brief are included, with verification added because without it
this is just another issue-creation button.

   1. Jira connection          connect, test, disconnect, health status
                               (API token auth; per user+project)
   2. Jira project mapping     project, issue type, priority, assignee,
                               labels, severity->priority map
   3. Manual "Create Jira Issue" from a Site Auditor finding, with an
                               editable preview
   4. Finding <-> issue mapping stored in jira_issue_links
   5. Duplicate prevention     the fingerprint plus a UNIQUE index
   6. Jira status retrieval    on demand and on load
   7. Basic status sync        webhook where available, reconcile poll
                               always, mapped on statusCategory
   8. "Open in Jira" link      everywhere a link exists
   9. Sync and error logging   jira_sync_logs, the activity card, a retry
                               button
  10. Secure credential handling  AES-GCM, never exposed, never logged
  11. SEO verification         the re-check on resolution, with verified /
                               reopened states
      -- item 11 is an addition to the brief's list and is argued for
         below.

29.2 WHY VERIFICATION IS IN THE MVP
-------------------------------------
Items 1-10 describe a competent but ordinary Jira connector; several SEO
tools have one. Verification is the thing only a tool that can re-crawl can
do, and it is what turns the integration from "we filed a ticket" into "we
proved it was fixed". It is also cheap to add at this point because the
schema (verification_spec on the link row) and the job runner both have to
exist for items 7 and 9 anyway. Deferring it would mean shipping the
plumbing without the payoff.

If the timeline forces a cut, cut item 3's AI preview and the comment
mirroring - not verification.

29.3 MVP FINDING COVERAGE
--------------------------
Site Auditor only, all 15 categories (3.1), plus Robots.txt Analyzer,
sitemap findings and Speed. That is the highest-volume, highest-value,
best-structured finding set, and the panel component is built to be
reusable so the other modules are a small follow-up (17.7).

29.4 EXPLICITLY POSTPONED
--------------------------
  Phase 4   automatic issue creation, severity rules, automation config
  Phase 5   AI-generated descriptions
  Phase 6   the dashboard card, the funnel, resolution metrics, the
            rollout to wpscan/schema/w3c/eeat/duplicates/backlinks/onpage/
            screaming-frog
  Later     comment mirroring (7.2 - phase 3 if cheap, otherwise later)
            bulk/batched issue creation (4.6)
            OAuth 2.0 3LO (4.1)
            email notifications (19.4)
            everything in Section 30

29.5 MVP DEFINITION OF DONE
-----------------------------
  [ ] a user connects Jira and maps a project in under two minutes
  [ ] a finding becomes a Jira issue with a useful description in one click
      plus a confirm
  [ ] clicking twice does not create two issues
  [ ] a developer moving the ticket to Done causes SEOX to re-check the URL
      unattended and show verified or reopened
  [ ] every failure is visible, explained and retryable
  [ ] the token is encrypted, never returned and never logged
  [ ] with Jira disconnected, SEOX is byte-identical to before (24.7)
  [ ] the preview-mount test passes and /api/jira/status answers on :4173

SECTION 31 - FINAL ARCHITECTURE RECOMMENDATION
================================================================================

31.1 OUTBOUND - SEOX TO JIRA
------------------------------
  React page (AuditorIssueDetail / JiraPanel / Dashboard)
        |  src/lib/jiraApi.js      (Bearer session token)
        |  src/lib/jiraCache.js    (projectDataStore, per-key, single-flight)
        v
  /api/jira/*                       mounted by vite.config.js for BOTH
                                    configureServer and configurePreviewServer
        |  functions/api/jira/<route>.js
        |    configureMysqlConnection(env)
        |    requireUser + requireJiraProject
        |    consumeRateLimit('jira:*')
        v
  Jira Integration Service          functions/_lib/jira-*.js
        |    jira-fingerprint  (dedupe)
        |    jira-issue-builder (ADF)
        |    jira-ai            (optional enrichment)
        |    jira-repository / jira-store   (MySQL)
        |    jira-client        (timeout, retry, 429, SSRF, breaker)
        v
  Jira Cloud REST API v3

31.2 INBOUND - JIRA TO SEOX
-----------------------------
  Jira Cloud
        |  webhook (jira:issue_updated, comment_created, issue_deleted)
        |  filtered by JQL  labels = "seox"
        v
  POST /api/jira/webhook?t=<secret>
        |  constant-time secret check, size and shape validation,
        |  per-connection rate limit
        v
  Idempotency + durable inbox      jira_webhook_events (UNIQUE event_key)
        |  200 OK returned here, in under a second
        v
  Synchronisation layer            functions/_lib/jira-jobs.js runner,
                                   driven by POST /api/jira/jobs on a timer
        |    jira-sync         (statusCategory -> seox_state, ordering check)
        |    jira-verify       (re-fetch the URL, run the checks)
        |    jira_comment / jira_transition  (the only writes back)
        v
  SEOX database                    jira_issue_links, jira_sync_logs
        |
        v
  SEOX UI                          badges, panel state, dashboard counts
                                   (read from SEOX's own database - never
                                    from Jira at render time)

  Reconciliation floor: 'jira_reconcile' every 30 minutes issues ONE JQL
  search per project and applies the same synchronisation layer, so the
  system is correct even if no webhook is ever delivered.

31.3 RESPONSIBILITIES
----------------------
  SEOX OWNS
    detecting SEO issues and classifying severity
    the finding taxonomy (issue slugs)
    the fingerprint and the finding <-> issue mapping
    the SEO recommendation and acceptance criteria
    RE-CHECKING THE LIVE SITE and deciding whether the problem still exists
    the SEO-side state (open / verified / reopened)
    its own audit trail

  JIRA OWNS
    the work item and its identity (the issue key)
    workflow status and transitions
    assignee, priority after creation, sprint, board position
    developer discussion (comments)
    team notifications and reporting on throughput

  NEITHER CROSSES
    SEOX never closes, reassigns, reprioritises or deletes a Jira issue.
    Jira is never the source of truth for whether an SEO problem exists.
    The 'reopened' state is where the two views are allowed to disagree,
    visibly, on purpose.

31.4 THE FIVE DECISIONS THAT MATTER MOST
------------------------------------------
  1. Register every route for configurePreviewServer as well as
     configureServer. Production is vite preview on :4173.
  2. Deduplicate on a server-computed fingerprint enforced by a UNIQUE
     index, never on the issue title.
  3. Map on Jira's statusCategory, never on the status name.
  4. Store a verification_spec on the link row at creation time, because
     the crawler runs in the browser and will not be there when the ticket
     closes.
  5. Keep Jira off every pre-existing request path, so it can never take
     SEOX down.

DEVIATIONS FROM THE PLAN, AND WHY
  1. jira_connections gained a `webhook_secret_lookup` CHAR(64) column.
     Section 12.1 stored only the encrypted secret - which cannot appear in a
     WHERE clause, so the webhook could not find its connection. The column
     holds sha256(secret); the decrypted secret is still compared in constant
     time before the row is trusted.

  2. jira_jobs job types are jira_verify | jira_reconcile | jira_webhook |
     jira_reopen | jira_prune. The plan also listed jira_create, jira_sync,
     jira_comment, jira_transition and jira_auto_scan. Creation stays
     synchronous (the user is waiting for the issue key), and commenting and
     transitioning happen inside the verify/reopen handlers rather than as
     separate queue hops - fewer moving parts for the same behaviour.
     jira_auto_scan belongs to Phase 4.

  3. Section 14.5 said a 429 should not consume a retry attempt; gbp-jobs.js
     does consume one. The Jira runner implements the improvement
     (retryJob(..., { consumeAttempt: false })) rather than copying the
     existing behaviour.

  4. Timestamp handling is stricter than the plan described. mysql2 returns
     DATETIME columns as JS Date objects and Jira sends ISO strings, so
     jira-status-map.js gained toEpochMs/toIso and every API response
     normalises to ISO. A test caught the original naive comparison, which
     silently produced an Invalid Date and would have made the staleness check
     a no-op.

  5. Section 24.8's preview-mount test additionally asserts that the existing
     API plugins still register their preview hooks, so a future change cannot
     quietly drop one while adding another.
